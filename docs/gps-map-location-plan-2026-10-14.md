# GPS 품질 확인·지도에서 정류소 위치 확인 — 협의 계획

> **현재 구현 기록 — 2026-10-15:** 사용자 “개선방안을 적용해서 푸시해.”와 후속 “ㄱㄱ”에 따라 웹·iPhone 구현과 검증·push 작업을 진행한다. 최신 범위·차이·검증·원격 상태는 [구현·검증 기록](citizen-capture-implementation-2026-10-15.md)을 기준으로 확인한다. 아래의 승인 이력과 “구현 대기/미확정/푸시 직전” 표시는 각 논의 당시의 역사 기록이며 이후 포괄 실행 지시와 구분한다. 당시 법령 조사·가상 사례를 실제 사진 AI 검증 결과로 바꾸지 않는다.

작성일: 2026-10-14 (한국 시각). 상태: **부분 확정·기능 구현 전. 촬영 방향 기능과 주변 정류소 후보 수집·선정안은 확정 완료·구현 대기. 나머지 지도/GPS 세부안은 협의 중**.

상위 기록: [민원인 촬영·유형 인식 개선 협의](citizen-capture-improvement-plan-2026-10-13.md). 전체 계획 확정 후 웹과 iPhone에 함께 구현하고 푸시 전 상태에서 설명하는 절차를 유지한다. 2026-10-14에 촬영 방향 기능을 확정했고, 이어 주변 정류소 선정안도 별도 확정했다. GPS 숫자 기준·지도 공급자·버스정류소 전체 안의 일괄 확정으로 확대하지 않는다.

2026-10-14 공통 촬영 흐름 확정 후, 상위 기록 11절에서 카카오 우선 공급자·이 문서의 지도 위치 확인/저장 흐름·GPS 초기값을 묶어 적용하는 권장안을 제시했다. 값은 조정 가능한 설정으로 관리하고 변경 이유를 남기는 제안이며 아직 미확정이다. 이번 공통 촬영 흐름 승인을 지도/GPS 설정 승인으로 확대하지 않는다.

## 1. 사용자 요청과 검토 결론

> 순서대로 한번 진행해봐. GPS 품질 확인은 어떻게 하지? 그리고 현재 주소에서 정류장에서 가까운지 아닌지는 보통 카카오맵이나 네이버맵에서 내 위치 찍어서 보는게 정확하다고 보거든? 그방식으로 구현할 수 있는지 검토해보고 계획을 수립.

직접 현장 검증이 어렵다는 앞선 제약을 유지한다. 제안은 **GPS 품질 확인 → 지도에서 내 위치·사진 위치·주변 정류소 확인 → 필요할 때 신고할 차량 위치 지정 → 사진 속 정류소 근거 대조**다.

카카오·네이버 모두 공식 지도 기능으로 구현할 수 있다. 공식 웹 예제는 브라우저 Geolocation으로 얻은 좌표를 지도에 표시한다. 지도 SDK 교체 자체가 GPS 센서 정밀도를 높인다는 근거는 없으며, 각 소비자용 지도 앱의 내부 위치 보정 알고리즘과 동일하다고도 약속하지 않는다. 이 프로젝트에서 얻을 이점은 도로·건물·정류소를 같은 화면에서 확인하고 잘못 선택한 위치를 보완하는 기능이다.

주소 글자, 주소 검색의 대표 좌표, 촬영자의 현재 좌표, 사진 촬영 당시 좌표, 차량 위치, 정류소 좌표를 구분한다. 주소 검색 결과는 지도를 해당 지역으로 이동할 때 쓰며 도로변의 차량 좌표나 10m 경계의 기준점으로 자동 대체하지 않는다.

`accuracy`가 없는 경우 0m로 표시하지 않는다. 현재 주소 시트의 `accuracy ?? 0` 문구도 함께 보완할 대상이다. 원이 그려진다고 실제 위치가 항상 그 안에 있다는 의미는 아니다.

## 3. GPS 품질 확인 순서

1. 촬영 화면이 활성화되면 기존 연속 위치 수신을 활용한다. 받은 좌표의 범위·숫자 유효성과 위치 취득 시각을 확인한다. 웹의 취득 시각과 iPhone의 위치 timestamp를 각각 사용한다.
2. 최근의 짧은 구간을 메모리에 보관한다. 같은 취득 시각의 재수신을 여러 번의 독립 측정으로 세지 않는다. 실제 플랫폼이 새 값을 주지 않으면 샘플 수가 부족하다고 기록한다.
3. **최신성, 단말 보고 오차, 위치값의 일관성, 권한·위치 사용 가능 여부**를 따로 평가한다. 한 점의 점수나 AI 추정 정확도로 합치지 않는다.
4. 초기안에서는 최신 유효 좌표와 품질 상태를 사용한다. 평균을 내서 새 정확한 좌표가 생긴 것처럼 표시하지 않는다. 급격한 이동은 GPS 튐과 실제 사용자 이동을 구분하기 어려우므로 이유를 ‘위치 변화 큼’으로 남기고 정밀 판단을 보류한다.
5. 셔터 시점에 위치 취득 시각과 사진 촬영 시각의 차이를 기록한다. 그 뒤 도착한 위치로 기존 사진의 GPS를 덮어쓰지 않는다. 재촬영·추가 촬영은 각 사진에 별도로 연결한다.
6. ‘현재 위치 다시 찾기’는 새 위치 수신을 요청하되 사진 촬영을 막지 않는다. 제한 시간 내 받지 못하면 재시도·지도 확인을 제공한다. 화면을 닫으면 수신·요청을 정리하고 늦은 결과를 무시한다.

### 초기 설정 제안 — 미확정, 성능 보증값 아님

아래 수치는 먼저 모의 입력으로 동작을 비교하기 위한 설정 초안이다. 정류소 탐색의 상태를 정하기 위한 값이며 법적 거리 기준이나 실측 정확도 기준이 아니다.

| 확인 항목 | 초기 설정 제안 | 결과 처리 |
| --- | --- | --- |
| 수신 이력 | 최근 10초, 서로 다른 취득 시각의 값 최대 20개 | 위치 변화와 새 값 여부 확인. 반드시 이만큼 수신된다고 가정하지 않음 |
| 최신성 | 마지막 위치 취득 후 5초 이내를 최근 값으로 분류 | 그보다 오래되면 ‘위치 갱신 필요’. 시간만으로 촬영 차단하지 않음 |
| 보고 오차 | 20m 이하 / 20m 초과~50m 이하 / 50m 초과 또는 알 수 없음 | 주변 탐색 참고 가능 / 넓은 범위로 참고 / 지도 확인 필요. 20m 이하도 차량 10m 안/밖 판정 허용을 뜻하지 않음 |
| 일관성 | 최근 서로 다른 값 3개 이상에서 기준점과의 간격이 각 보고 오차 반경 합 안에서 설명되는지 확인 | 겹침은 ‘서로 모순이 작음’만 의미. 실제 위치 정답이나 독립 표본으로 해석하지 않음. 부족하면 ‘안정성 확인 중’ |
| 재확인 제한 | 요청 후 최대 15초 | 이전 기록을 보존한 채 실패 사유·재시도 제공 |

큰 오차 원이 겹친다고 좋은 품질로 바꾸지 않는다. 시간은 신선하지만 권한이 대략적 위치만 허용되거나 보고 오차가 큰 경우도 따로 표시한다. 웹과 iPhone이 보고하는 정확도 의미·권한 차이를 기록하고 두 플랫폼에서 동일한 통계적 신뢰도를 보장한다고 표현하지 않는다.

화면 문구 초안: ‘위치 확인 중’, ‘주변 정류소를 찾을 수 있어요’, ‘위치 범위가 넓어요’, ‘위치를 다시 확인해 주세요’. 필요한 경우 ‘마지막 확인 3초 전 · 단말 보고 오차 약 18m’처럼 이유를 볼 수 있게 한다. ‘위치 정확함’ 또는 ‘10m 이내 확정’으로 표시하지 않는다.

## 4. 지도에서 확인하는 사용자 흐름

1. **지도 열기:** 촬영 전에는 현재 위치를 중심으로, 촬영 후에는 해당 사진의 촬영 위치를 중심으로 연다. 오래된 사진을 확인할 때 지금 사용자의 위치를 사진의 장소로 취급하지 않는다. 사진 좌표가 없으면 주소 검색이나 지도 선택을 안내하며 기본 위치를 실제 위치처럼 표시하지 않는다.
2. **위치 표시:** ‘현재 내 위치’, ‘사진 촬영 위치’를 텍스트와 모양으로 구별하고 GPS에는 단말 보고 오차 원을 표시한다. 사용자가 지도를 이동하면 자동 따라가기를 중단해 화면이 다시 끌려오지 않게 한다.
3. **주변 정류소 표시:** 식별 가능한 공공 정류소 자료를 자체 마커로 올린다. 지도 배경의 정류소 아이콘을 그대로 API 데이터로 읽을 수 있다고 가정하지 않는다. 정류소 이름·공개 번호·자료 기준일을 함께 보여주고 가까운 여러 후보를 유지한다.
4. **정류소 선택:** 사용자가 표지를 보고 해당 정류소를 선택하거나 사진에서 읽힌 번호를 대조한다. 가장 가까운 정류소를 자동으로 확정하지 않는다. 선택 결과는 `사용자 선택`과 `사진 근거 대조`를 따로 기록한다.
5. **거리 표시:** 차량 위치가 없으면 ‘촬영 위치에서 선택한 정류소 좌표까지 약 ○m’로 출발점과 도착점을 명시한다. 차량 위치를 지도에서 직접 지정한 경우 ‘사용자가 지정한 차량 위치 기준 지도상 약 ○m’로 표시한다. 두 좌표 사이 참고 거리는 기존 거리 계산을 재사용할 수 있으나 지도 거리·도보 경로 거리·법적 거리 기준점을 혼합하지 않는다.
6. **선택 보완:** 필요한 경우에만 지도에서 차량 위치를 지정한다. ‘현재 내 위치’나 주소 검색 결과를 차량 위치로 자동 복사하지 않는다. 사용자가 주변 건물·도로를 보고 선택해도 실제 측량 성공으로 기록하지 않는다.
7. **저장·취소:** 선택한 좌표·정류소·주소 변경안을 먼저 보여주고 ‘이 위치 사용’에서 저장한다. 저장 완료 전까지 기존 자료를 유지한다. ‘취소’는 지도 열기 전의 확정 좌표·주소·사진으로 돌아가며 수동 주소는 명시적인 변경 동작 없이 덮어쓰지 않는다.

지도 확대 자체가 좌표를 정확하게 만들지는 않는다. 현재 주소는 장소 탐색을 돕고, 거리 계산은 역할과 출처가 확인된 좌표로 수행한다. 실제 차량과 정류소 기준점의 위치 품질을 모르면 10m 경계 판정은 미확인으로 남긴다. 이는 지도 기능 미완료가 아니라 결과의 의미를 구분하는 규칙이다.

### 촬영 방향 표시·정류소 방위 대조 — 확정 완료·구현 대기

2026-10-14 사용자 질문 “지도에서 사진찍을 때 방향까지도 보면서 인식할 수 있지 않은지”에 대한 설명 후, 사용자가 다음과 같이 확정했다.

> "이대로 확정"

확정 범위는 촬영 위치·카메라 방향을 함께 표시하고, 셔터 시점의 위치·방향·취득 시각을 사진에 연결하며, 품질이 충분할 때 정류소 후보의 방위를 대조하는 보조 기능이다. 웹·iPhone에 같은 의미로 구현하고 센서 미지원·권한 거부·품질 부족 시 기존 사진 분석과 수동 선택을 계속 제공한다. 방향 확정 당시 세부 센서 기준값·정류소 선정 규칙·지도 공급자는 별도 협의·검증 대상으로 남겼으며, 정류소 선정안은 아래의 후속 발언으로 별도 확정되었다.

- **기대하는 역할:** 촬영자의 위치에서 각 정류소로 향하는 방위와 카메라의 수평 촬영 방향을 비교해 일치하는 후보를 우선 대조한다. 사진 속 공개 번호·표지·차량 관계와 함께 사용하며 지도 방향만으로 사진에 정류소가 보인다고 결론 내리지 않는다.
- **수집·계산:** GPS는 촬영 위치, 방향 센서와 기기 자세는 카메라가 바라보는 방향에 사용한다. Geolocation의 이동 방향은 사용하지 않는다. 기기 상단의 나침반 값도 그대로 카메라 방향으로 쓰지 않고 실제 카메라 축·기울기·세로/가로 촬영·회전을 반영한다. 웹은 북쪽 기준 방향을 얻을 수 있는지부터 확인하고, iPhone은 Core Location/Core Motion을 통해 기준 좌표계와 센서 상태를 관리하는 안이다.
- **북쪽 기준과 상태:** 지도 방위와 센서가 참북/자북 중 어떤 기준인지 맞추고 출처·기준·관측 시각·유효성·제공되는 오차를 기록한다. 상대 회전만 있거나 북쪽 기준/보정이 불명확하면 동서남북을 임의로 지정하지 않는다. 신뢰도 수치가 없으면 센서 품질 미확인으로 둔다.
- **촬영 화면:** 지도에 내 위치와 촬영 방향 화살표를 표시한다. 주변 정류소 마커와 함께 사용하되 카메라의 차량·번호판 확인을 가리지 않는 보조 화면으로 제공한다. 화각·줌·렌즈 정보를 검증하지 못한 상태에서 정확한 촬영 범위처럼 부채꼴을 그리지 않는다. 참고 범위를 추가할 경우 의미를 표시하고 실제 사진 경계와 구분한다.
- **사진과 연결:** 셔터 시점에 가까운 위치·방향 표본을 해당 사진 ID에 연결하고 시간 차이를 남긴다. 촬영 후 휴대폰을 돌리거나 최신 센서 값이 도착해도 저장된 촬영 방향은 바뀌지 않는다. 방향이 없는 과거 사진·앨범 사진에는 현재 방향을 붙이지 않는다.
- **후보 대조:** 방위각 차이는 0°/360° 경계를 감안해 계산한다. 우선은 순위 보조로 사용하고 방향 하나만으로 후보를 삭제하지 않는다. 사진 번호와 방향이 충돌하면 원인 확인/보류 상태로 남긴다. GPS 오차 범위가 정류소까지의 거리와 비슷하거나 더 크면 지도 방위 자체가 불안정하므로 방향 순위 반영을 중단한다. 거리·센서 오차·화각을 고려한 기준값과 가중치는 아직 미정이다.
- **사용하지 않을 상황:** 오래된 방향, 급회전, 큰 방향 변동, 센서 무효, 권한 거부, 지원 안 됨, 북쪽 기준 미확인, 카메라가 거의 수직으로 바닥/하늘을 향해 수평 방향이 불안정한 경우에는 방향 미확인으로 둔다. 촬영·사진 판독·수동 정류소 선택은 계속 가능하게 한다. 사용자 설정 변경이 필요하면 이유를 설명하고 사용자가 직접 처리하도록 한다.
- **효과의 한계:** 같은 방향에 정류소가 여러 개 있거나 같은 방향으로 거리만 다른 물체는 방향만으로 구분할 수 없다. 도로 같은 쪽/맞은편 여부, 시설의 실제 가시성, 차량의 정류소 10m 안/밖도 방향 하나로 확정하지 않는다. 기본 사진을 찍기 위해 위치를 옮기거나 다른 각도로 촬영하도록 강제하지 않는다.
- **비현장 검증:** 알려진 기기 자세와 카메라 축으로 북/동/남/서, 359°↔1°, 세로/가로, 전후면·미러링, 지도 회전, 수직 촬영, 사진 시각과 방향 수신 시각의 어긋남을 시험한다. GPS·나침반 오류, 같은 방향 복수 정류소, 반대편 후보와의 혼동도 주입한다. 계산·상태 처리 검증과 실제 기기 센서 정확도 검증을 구분한다.

이 기능은 현재 코드에 없다. 웹·iPhone 모두 같은 결과 의미와 실패 동작으로 추가하는 확정 계획이며, 실제 기기에서의 방향 정확도나 정류소 선택 개선율은 측정하지 않았다. 전체 계획이 끝난 후 구현하는 원칙을 유지한다.

### 주변 정류소 후보 수집·선정 — 확정 완료·구현 대기

확정일: 2026-10-14 (한국 시각). 사용자 발언:

> 정류소 선정안도 이대로 확정. 다음 진행해봐.

주변 여러 후보 수집, 사진 속 공개 번호 우선 대조, 이름·노선·위치·촬영 방향의 보조 활용, 추천 이유 표시, 모호한 경우 사용자 선택을 확정했다. 사진 근거와 위치/방향이 충돌하면 보류하며 기존 자료를 보존한다. 여기서 정하는 것은 정류소끼리의 선택이며, 원래 5번 개선인 위반 유형 간 우선순위 전체와 구분한다.

1. **후보 수집:** 사진 촬영 좌표와 위치 품질을 기준으로 주변 정류소 여러 곳을 수집한다. GPS가 없으면 명시적으로 선택한 지도 위치·주소 검색 지역을 탐색 출발점으로 사용할 수 있으나 사진 GPS와 구분한다. 조회 범위와 누락 여부를 기록하며 검색 반경을 차량의 위반 거리 기준과 동일하게 제한하지 않는다.
2. **자료 정리:** 제공기관·지역·공개 번호·내부 ID를 구분한다. 같은 이름이나 가까운 좌표만으로 서로 다른 정류소를 합치지 않는다. 현재 API의 첫 페이지 50건 제한처럼 결과가 잘릴 수 있는 구조에서는 필요한 범위의 페이지를 확인하거나 조회가 일부임을 표시한다. 누락을 ‘정류소 없음’으로 바꾸지 않는다.
3. **사진 근거 우선 대조:** 읽을 수 있는 공개 정류소 번호가 후보 자료와 일치하는지 확인한다. 번호 체계가 연결되지 않거나 숫자가 흐리면 일치로 간주하지 않는다. 이름·노선 안내·사진상 도로 쪽은 보조 근거로 사용한다. 번호가 읽히지 않아도 사진 분석을 계속한다.
4. **방향과 위치 활용:** 확정한 방향 기능을 품질이 충분할 때만 순위 보조로 사용한다. 거리와 방향만으로 정류소를 확정하거나 후보를 제거하지 않는다. 공개 번호 일치와 방향·위치가 충돌하면 보류 사유를 표시한다.
5. **사용자 표시:** 근거가 모인 후보를 먼저 보여주고 ‘사진 번호 일치’, ‘촬영 방향과 비슷함’, ‘가까운 후보’처럼 이유를 구분한다. 초기 화면은 상위 후보 최대 3개와 전체 후보 보기로 제안하되, 화면에 먼저 보이는 3개만 내부 분석에 남기는 방식은 아니다. 선택을 매 촬영마다 강제하지 않는다.
6. **확인·저장:** 후보 하나에 충분한 근거가 모이면 추천하고, 상충하거나 복수 후보가 남으면 정류소 선택을 요청한다. 선택한 정류소 ID·자료 출처·사진 근거·사용자 선택 여부를 별도로 저장한다. 사용자 선택만으로 사진 식별 성공 또는 차량 10m 이내라고 기록하지 않는다. 취소·조회 실패·저장 실패 때 기존 자료를 보존한다.

비현장 검증은 동명·맞은편·같은 방향 복수 정류소, 사진 번호가 GPS 최근접 후보와 다른 경우, 흐린 번호·중복 번호 체계·일부 페이지 누락·GPS 없음·방향 미지원·상충 사례로 구성한다. 기존 최근접 방식과 모의 조건에서의 후보 누락·오선택·보류·질문 빈도를 비교한다. 번호 판독 성능과 실제 현장 거리 정확도는 이 시험으로 검증했다고 하지 않는다. 현재 이 세부안은 확정 완료·구현 대기이며 새 기능 코드·빌드·실기기 시험은 수행하지 않았다.

이후 2026-10-14 사용자 "사진 근거 확인이랑 보완 촬영안도 이대로 확정. 다음 진행해봐."에 따라 [상위 기록의 버스정류소 사진 근거·보완 촬영안](citizen-capture-improvement-plan-2026-10-13.md)도 확정 완료·구현 대기로 전환했다. 정류소 선정이 끝났다는 사실과 사진에서 대상 차량의 관계까지 확인됐다는 사실을 구분한다. 이어 횡단보도·어린이보호구역·인도와 공통 촬영 흐름도 각각 확정했다. 이후 사용자가 전용구역 3개도 유형별로 깊게 조사·시뮬레이션하도록 요청해 현재는 장애인 구역부터 협의한다. 상위 기록의 적용 범위가 갱신되었으며 이후 진행 상태는 상위 기록을 따른다. 지도 공급자·GPS 숫자 기준은 이번 권장안의 사용자 확정 전까지 미확정으로 유지한다.

## 5. 지도 공급자 검토와 권장안

| 항목 | 카카오 지도 | 네이버 지도 |
| --- | --- | --- |
| 웹의 내 위치 표시 | 공식 Geolocation 예제 확인 | 공식 Geolocation 예제 확인 |
| 지도 위 마커·선·원과 위치 선택 | Web SDK 사용 가능 | JavaScript API 사용 가능 |
| iPhone | KakaoMapsSDK v2 + Core Location 연결 검토 | iOS SDK 위치 추적·위치 오버레이 문서 확인 |
| 기존 프로젝트와 연결 | 좌표→주소 Kakao REST 코드가 이미 있음. 지도 SDK는 새 연결 필요 | 현재 지도·주소 연결이 없으므로 신규 연결 필요 |
| GPS 정확도 개선 보장 | 지도 SDK 도입만으로 보장하지 않음 | 지도 SDK 도입만으로 보장하지 않음 |

**권장 초안은 카카오 지도 한 곳을 웹·iPhone의 공통 지도 공급자로 우선 연결하는 것이다.** 기존 Kakao 주소 API 경로를 활용할 수 있다는 유지보수 관점의 선택이며, 카카오가 네이버보다 위치 측정이 정확하다는 판단이 아니다. 네이버를 선호하면 같은 데이터·사용자 흐름으로 공급자를 바꿀 수 있게 지도 표시와 위치·판단 로직을 분리한다. 두 SDK를 처음부터 동시에 탑재하거나 위치 결과를 평균낼 계획은 아니다.

카카오 지도 Web은 JavaScript 키, iOS는 네이티브앱 키가 필요하다. 현재 REST 키 설정만으로 지도 SDK가 준비되어 있다고 취급하지 않는다. 구현 시 API 활성화·등록 도메인·iOS 앱 식별자·현재 쿼터/과금 조건을 확인한다. 이 계획 단계에서는 계정 설정·결제·키 발급을 변경하지 않았다. 비밀 키는 서버에 유지하고 플랫폼용 식별 키도 저장소에 실제 값을 넣지 않는다.

공식 SDK로 앱 안에서 확인·선택을 완료하는 흐름을 기본으로 한다. 외부 카카오맵·네이버지도 열기는 보조 확인으로 검토할 수 있지만 외부 앱의 파란 점이나 사용자의 선택이 자동으로 이 앱에 되돌아온다고 가정하지 않는다. 지도 불러오기 실패 시 사진·주소 수동 입력·보관은 계속할 수 있어야 한다.

| 5 | iPhone Core Location + 지도 SDK를 SwiftUI에 연결 | 같은 의미의 상태·선택·저장·취소 동작. 사용 중 위치 권한부터 적용 |
| 6 | 회귀·모의 위치·지도 연결 검증 후 설명 자료 정리 | 웹/iPhone 구현·빌드·실행·시뮬레이션·실기기 미검증 상태를 별도 보고 |

iPhone은 위치·지도 통합이 새 작업이다. 카메라 구조는 기존 AVFoundation을 이어가며 사용자 기기 설정 변경이 필요하면 사용자가 직접 처리하도록 안내한다. 이번 단계에서 AR·LiDAR·새 거리 측정 모델을 구현하지 않는다.

## 7. 현장 검증 없이 수행할 검증

- **품질 로직:** 신선/오래된 값, 중복 취득 시각, 좋은 값 다음 큰 튐, 실제 이동, 계속 같은 방향으로 치우친 값, 정확도 없음·오류, 샘플 부족, 권한 거부·대략적 위치·타임아웃을 주입한다. 고정 편향의 실위치를 알 수 없는 한계는 그대로 남기며 ‘확실히 정확함’을 출력하지 않는지 검사한다.
- **경계값:** 위 초안의 시간·보고 오차 경계 전후에서 상태가 의도대로 바뀌는지 확인한다. 초기 수치가 현장 최적값으로 검증됐다고 표현하지 않는다.
- **지도 동작:** 새 위치 버튼, 과거 사진 위치 복귀, 지도 드래그 중 자동 이동 중단, 위치 새 수신 이후에도 사용자 차량 핀 유지, SDK/주소/시설 조회의 실패·늦은 응답을 확인한다.
- **보존과 호환:** 취소·저장 실패·새로고침·재열기·구버전 사진에서 GPS/주소/사진이 유지되는지 확인한다. 미확인 accuracy를 0으로 채우지 않는다.
- **정류소 선택:** 공개 자료와 알려진 좌표를 이용해 반대편·동명·누락·오래된 자료·공개 번호 충돌 사례를 구성한다. 사진과의 일치는 적법하게 확보한 이미지가 있을 때 별도 평가하며 지도 자료로 사진의 정답을 억지로 만들지 않는다.
- **플랫폼:** 웹 모의 Geolocation과 iPhone 위치 서비스 시험 대체물·시뮬레이터의 위치 입력을 사용한다. SDK 지도 실행에는 유효한 플랫폼 설정이 필요하며 모의 지도 통과와 실제 지도 연결 성공을 구분한다.
- **보고:** 자동 테스트·지도 연결·빌드·시뮬레이터 성공을 실제 GPS 정밀도·현장 촬영 정확도 검증으로 보고하지 않는다. 사용자 현장 시험을 전체 코드 구현의 선행 조건으로 두지 않는다.

이번 작성 시점에는 문서·기존 코드·공식 SDK 자료만 검토했다. 새 위치 로직·SDK 연결·실제 API 인증·빌드·화면 실행·실기기 검증은 수행하지 않았다.

## 8. 확인한 공식 자료

- [카카오 Web — Geolocation으로 마커 표시](https://apis.map.kakao.com/web/sample/geolocationMarker/): 브라우저 위치로 지도에 현재 위치를 표시하는 예제.
- [네이버 Web — HTML5 Geolocation](https://navermaps.github.io/maps.js.ncp/docs/tutorial-6-map-geolocation.example.html): 브라우저가 제공한 좌표로 지도 이동.
- [카카오맵 제공 방식·키·설정](https://developers.kakao.com/docs/ko/kakaomap/common): Web/iOS SDK, 플랫폼 키 구분, 활성화·등록 설정·쿼터 안내.
- [KakaoMapsSDK v2 iOS 프로젝트 시작](https://apis.map.kakao.com/ios_v2/docs/getting-started/gettingstarted/): iPhone 지도 연결 참고.
- [네이버 iOS 위치](https://navermaps.github.io/ios-map-sdk/guide-ko/4-2.html): 위치 추적·권한·위치 오버레이.
- [W3C Geolocation](https://www.w3.org/TR/geolocation/): 취득 시각·accuracy·고정밀 요청의 의미. 보고 오차는 실제 위치의 절대 상한이 아님.
- [Apple CLLocationManager](https://developer.apple.com/documentation/corelocation/cllocationmanager): iPhone 위치 관리 연결.
- [Apple Xcode 위치 시뮬레이션](https://help.apple.com/xcode/mac/current/en.lproj/dev1b4074150.html): 실제 이동 없이 위치를 주입하는 개발 검증.
- [W3C Device Orientation and Motion](https://www.w3.org/TR/orientation-event/): 기기 축·상대/절대 자세·권한 및 화면 뒤쪽을 향한 벡터의 수평 방위 계산 예제. 명세 지원과 브라우저별 실제 지원을 구분한다.
- [Apple 기기 방향과 이동 방향](https://developer.apple.com/documentation/corelocation/getting-heading-and-course-information): heading과 course의 의미 구분.
- [Apple headingAccuracy](https://developer.apple.com/documentation/corelocation/clheading/headingaccuracy?language=objc): 방향 오차와 무효 상태. 나침반 간섭이 있는 경우도 별도 처리한다.
