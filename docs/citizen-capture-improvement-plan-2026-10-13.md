## 4. 4번 공통 촬영·보완·이어하기 흐름 — 확정 완료·구현 대기

2026-10-14 인도 안 확정 후 구체화한 통합안이다. 각 유형에서 확정한 원본 우선 확인·부족한 사진만 보완·기존 자료 보존 원칙을 유지하면서, 여러 사진과 여러 부족 사유가 함께 있을 때의 순서·기본 사진 지정·재촬영·이어하기 동작을 정한다.

**2026-10-14 사용자 확정: "공통 촬영 흐름도 이대로 확정. 다음 개선사항 진행해봐."** 아래 기본 사진 ID 지정·복수 역할 보완사진·촬영/분석 분리·부족 사유 묶음 안내·기본 쌍 재촬영·저장/이어하기·이전 자료 호환·웹/iPhone 검증 계획을 확정 완료·구현 대기로 전환한다. 다음 협의는 4번 적용 범위·지도/GPS 초기 설정과 교차로 확정 대기를 정리하는 권장안이다. 전체 계획 확정 후 구현하는 순서를 유지하며 기능 구현은 시작하지 않았다.

### 확인한 현재 구조

- [웹 사진 모델](../src/types/report.ts)의 `Shot`은 촬영 시각·위치·출처·이미지를 갖지만 사진별 영구 ID·역할·분석 대상 버전은 없다. `DraftReport.shots`와 `reads`는 같은 배열 순서를 이용한다.
- [웹 앱](../src/App.tsx)은 새 촬영본을 최대 두 장으로 잘라 저장하고, [분석 요청](../src/lib/vision.ts)도 앞의 두 장만 보낸다. 보완사진을 단순히 기존 배열 뒤에 추가하면 저장 또는 판독에서 빠질 수 있다.
- [촬영 흐름](../src/components/CaptureFlow.tsx)은 첫 사진 확인→대기→두 번째 사진으로 이어진다. 촬영 시각 기반 남은 시간 계산은 이미 있으므로 새로 만든 기능으로 보고하지 않는다. 분석 상태와 보완 안내가 두 번째 기본 촬영을 막지 않도록 확장한다.
- [기존 재촬영](../src/lib/replacement.ts)은 첫 사진을 다시 찍는 후보에서 두 사진을 제외하고, 두 번째 재촬영 후보에서는 첫 사진을 남긴다. 기존 저장본은 교체 저장 완료 전까지 보존한다. 통합안에서는 새 기본 쌍의 유효성과 이전 사진의 보관을 분리한다.
- [웹 보관함](../src/lib/reports.ts)은 저장 완료·실패 구분, 직렬 저장, 이전 기록 이어하기를 이미 지원한다. 새 통합 상태와 보완사진에도 이를 적용하며 기존 기능 전체를 신규 구현으로 설명하지 않는다.
- iPhone에는 별도 `TrialPhoto` 사진/영상 보관과 `ZoneEvidence`의 사진 ID·복수 역할·출처를 저장하는 전용구역 흐름이 있다. 웹의 기본 두 장·AI 흐름과 동일하지 않다. 기존 SwiftUI·AVFoundation 촬영과 보관 자료를 유지하면서 기본 유형의 통합 촬영 흐름을 연결하는 신규 작업이 필요하다.

### 사용자 흐름 제안

1. **첫 번째 기본 사진 촬영·저장:** 사진을 보존하고 촬영 시각을 기준으로 다음 촬영까지 남은 시간을 계산한다. 전체 분석을 시작하되 저장 상태와 분석 상태를 분리해서 보여준다.
2. **기본 사진에 필요한 정보부터 확인:** 대상 차량·번호판·장소 관계가 부족하면 원본 재분석을 먼저 하고, 필요할 때 해당 기본 사진 재촬영을 우선 안내한다. 선택한 유형의 시설 근거만 부족하면 보완 항목으로 남긴다. 분석 실패를 사진 부족으로 바꾸지 않는다.
3. **두 번째 기본 사진 촬영:** 적용 간격이 지나면 AI가 응답 중이거나 통신이 실패했어도 촬영·저장할 수 있게 한다. 이전 사진을 참고하는 촬영 안내를 유지한다. 분석이 미완료인 상태에서 다음 촬영을 허용하는 것이 점검 통과를 의미하지 않는다.
4. **기존 두 사진과 원본으로 부족 사유 재정리:** 두 번째 사진에서 해결된 항목은 보완 목록에서 제거한다. 각 기본 사진 자체의 필수 정보는 따로 확인한다. 한 사진의 근거가 다른 기본 사진의 부족을 자동 대체하지 않는다.
5. **필요한 보완 안내 한 가지를 우선 표시:** 차량과 시설의 연결처럼 다른 확인의 전제가 되는 항목을 먼저 제시하고, 한 번의 촬영으로 여러 부족 사유를 해결할 수 있으면 묶는다. 나머지 항목도 목록에서 볼 수 있게 한다. 과태료 금액으로 촬영 순서를 정하지 않는다.
6. **보완 후 해당 항목 재확인:** 새 사진과 필요한 기존 사진/원본 부분을 연결해 분석한다. 이미 확인된 다른 항목을 이유 없이 처음부터 재분석하거나 반복 촬영시키지 않는다. 새 근거가 기존 관찰과 충돌하면 영향을 받는 항목은 다시 확인한다.
7. **미완료 상태로 저장·이어하기:** 추가 촬영을 못 하거나 현장을 떠나야 하면 남은 사유와 함께 저장한다. 다시 열 때 현재 사진·확인된 근거·남은 항목을 복원하고 장소/차량/시간 조건이 아직 맞는지 확인한다. 나중에 찍은 다른 차량·다른 시점 사진을 이전 사건의 연속 촬영으로 자동 연결하지 않는다.

기다리는 동안 이미 있는 사진을 검토할 수 있게 하되, 상세사진을 찍으러 이동하도록 강제하지 않는다. 기본 두 번째 촬영 시점이 되면 그 촬영을 우선 안내한다. 이미 시작한 촬영이나 저장은 강제로 중단하거나 결과를 버리지 않는다. 촬영 흐름을 진행할 수 있다는 상태와 사진 근거·지역 조건을 확인했다는 상태를 분리한다.

### 기본 사진과 보완사진의 역할

| 구분 | 저장·활용 방식 | 자동 처리하지 않을 것 |
| --- | --- | --- |
| 기본 사진 1·2 | 시간 비교에 사용하는 두 사진을 ID로 명시적으로 지정 | 배열의 앞 두 장이라는 이유만으로 기본 사진으로 간주하지 않음 |
| 보완사진 | 시설 상세·전체 관계·경계 등 한 장에 여러 용도 연결 가능 | 사진 역할 선택만으로 실제 근거가 확인됐다고 표시하지 않음 |
| 기본 사진의 추가 역할 | 기본 사진이 시설·관계 근거도 충분히 제공하면 재사용 | 같은 정보를 담으려고 새 사진을 요구하지 않음 |
| 원본 부분 분석 이미지 | 원본 ID와 자른 영역을 연결한 분석용 파생 자료 | 별도의 실제 촬영이나 기본 두 장으로 계산하지 않음 |
| 기존 영상의 추출 장면 | 영상 출처·추출 시점을 유지해 기존 기능과 자료 보존 | 독립 사진 두 장 또는 계속 정차의 증명으로 승격하지 않음 |

사용자가 사진 용도를 지정한 사실과 AI가 그 용도의 근거를 확인한 사실을 나눈다. 동일 촬영·동일 원본·그 자른 이미지를 기본 사진 두 장으로 중복 사용하지 않도록 원본 연결과 확인 가능한 파일 중복을 점검한다. 다른 시각에 비슷하게 찍힌 사진을 단지 화면이 비슷하다는 이유로 동일 원본이라고 확정하지 않는다.

### 여러 부족 사유가 있을 때의 동작

| 상황 | 제안하는 다음 행동 |
| --- | --- |
| 기본 사진 번호판과 시설 문구가 모두 불명확 | 원본을 먼저 확인하고 기본 사진 보완을 우선. 새 기본 사진에서 시설도 해결되면 별도 상세 촬영 제거 |
| 시설 종류는 확인됐지만 대상 차량과 연결이 안 됨 | 문구 상세를 다시 요구하기보다 차량과 시설의 관계를 보여주는 사진 안내 |
| 소화전·인도 등 여러 후보의 부족 사유가 겹침 | 같은 전경 사진으로 해결할 수 있는 항목을 묶음. 모든 후보의 사진을 일괄 요구하지 않음 |
| 대상 차량 또는 적용 시설이 모호함 | 대상 선택이 필요한 상태로 남겨 관련 사진을 불필요하게 계속 요구하지 않음. 질문 형태는 후속 6번에서 확정 |
| 통신·GPS·지도·지역 규정 문제 | 재시도·위치/자료 확인으로 안내하고 사진 재촬영 항목과 분리 |
| 충분한 근거가 있는데 응답이 반복됨 | 해결된 항목을 제거하고 같은 버전 사진에 같은 촬영 요청을 반복하지 않음 |
| 추가 촬영을 계속해도 불명확함 | 이유를 남기고 저장/나중에 이어가기를 제공. 무한 재분석·재촬영 안내를 하지 않음 |

사용자에게 보여줄 진행 상태는 '사진 저장됨 / 확인된 내용 / 남은 내용'으로 정리한다. AI의 신뢰도 숫자만으로 완료를 표시하거나 공식 신고 가능·법적 위반 확정으로 표현하지 않는다. 수동 유형 선택은 유지하고 유형 추천의 전체 우선순위는 후속 5번에서 확정한다.

### 재촬영·교체·저장 실패의 의미

- **보완사진 추가/교체:** 기본 두 장의 지정과 촬영 시각을 그대로 유지한다. 보완사진 때문에 시간 계산을 초기화하지 않는다.
- **두 번째 기본 사진 재촬영:** 첫 번째 사진은 유지하고 새 두 번째 사진과의 간격·동일 차량·장소 관계를 다시 확인한다.
- **첫 번째 기본 사진 재촬영:** 성공적으로 새 기본 사진으로 교체되면 새 촬영 시각을 기준으로 간격을 다시 계산한다. 이미 찍은 두 번째 사진이 새 첫 사진보다 앞선 시각이면 유효한 기본 쌍으로 통과시키지 않는다. 기존 두 번째 사진은 자동 삭제하지 않고, 새 두 번째 촬영이 필요하다는 상태로 남긴다.
- **교체 취소·실패:** 새 후보 저장이 성공하기 전까지 기존 기본 사진 지정·사진·입력값을 유지한다. 취소하면 기존 상태로 돌아가고 저장 실패면 재시도할 수 있다.
- **저장 상태:** 기기 저장 완료를 확인한 뒤에만 '저장됨'으로 표시한다. 실패한 새 자료는 화면에 남아 있음을 안내하되 앱 종료 후 복구를 보장하지 않는다. 저장 공간 문제를 해결하려고 기존 사진을 자동 삭제하지 않는다.
- **분석 상태:** 저장된 사진의 분석만 실패한 경우 해당 요청을 재시도한다. 사진·대상 차량·유형/시설 선택이 바뀌면 관련 분석의 입력 버전을 비교해 늦은 옛 응답의 덮어쓰기를 막는다. 수동 주소·본문·유형 변경은 보호한다.

### 기술 구조·이전 자료 호환·양쪽 플랫폼

- 배열 순서에 의존하는 사진 두 장 구조를 사진 목록과 명시적인 기본 사진 1·2의 ID 연결로 확장한다. 사진별 원본/촬영 ID, 출처, 촬영 시각, 추가 시각, 복수 용도, 분석 상태를 둔다. 원본과 분석용 이미지의 구분은 앞서 확정한 원본 보존 계획을 따른다.
- 부족 사유는 사유 ID·관련 사진/대상·필요한 행동·해결 여부로 관리한다. 사진 용도와 실제 관찰 근거를 분리하고, 한 사진의 여러 근거가 여러 부족 사유를 해결할 수 있게 연결한다. 구체 필드명과 내부 저장 배치는 구현 설계에서 정한다.
- 기본 두 장의 번호판·시간 비교 분석과 시설 상세·위치 관계 분석을 목적별로 요청한다. 현재 API에 사진 수만 늘려 보내거나 앞 두 장으로 잘리는 경로에 보완사진을 넘기지 않는다. 요청별 원본 ID·입력 버전·결과를 연결하고 변경된 항목 중심으로 재분석한다.
- 기록 버전과 호환 읽기를 두어 기존 웹 초안의 사진·촬영 시각·수동 입력을 보존한다. 종전 의미가 분명한 기본 사진 1·2만 연결하고 기존 누락 메타데이터는 미확인으로 남긴다. 옛 축소 사진에서 존재하지 않는 고해상도 원본을 복원한 것으로 처리하지 않는다.
- 이전 형식 변환은 새 기록 저장 성공 뒤에 전환하고, 실패한 변환이 기존 저장본을 덮어쓰거나 같은 사진을 반복 생성하지 않도록 한다. 기본 쌍 변경 후 제외된 사진은 자료 목록에서 보존하고 삭제는 사용자의 명시적 동작으로 처리한다. 원본은 사진별 한 번 저장하고 여러 역할에서 참조해 불필요한 복제를 줄인다.
- iPhone에서는 기존 사진/영상 및 전용구역 보관함을 유지하며 같은 의미의 기본 쌍·보완 용도·부족 사유·저장 상태·분석 연결을 추가한다. 기존 `ZoneEvidence`의 복수 역할 개념은 참고할 수 있지만 자료를 무조건 합치거나 기존 영상 기록을 기본 사진 쌍으로 변환하지 않는다. 두 플랫폼 간 자동 동기화는 이번 통합안에 포함하지 않는다.
- 새 사진 수·전송 용량·분석 호출 상한은 기기 저장 공간과 처리 비용을 검증해 정하고 한도에 닿으면 이유를 알린다. 이미 저장된 자료를 지우거나 새 사진을 조용히 무시하지 않는다. 상한 수치를 실제 측정한 값처럼 미리 약속하지 않는다.

### 검증할 결과

1. 기본 두 장+보완사진을 저장하고 앱/페이지를 다시 열었을 때 사진 역할·수동 입력·남은 사유가 유지되는지 확인한다.
2. 첫 사진 분석 지연·실패 중에도 두 번째 촬영이 가능하고, 미확인 상태를 완료로 잘못 바꾸지 않는지 확인한다.
3. 기본 사진 한 장이 여러 근거를 제공하거나 보완 한 장이 여러 사유를 해결할 때 중복 촬영 안내가 줄어드는지 확인한다. 이는 흐름 시험이며 실제 모델 정확도 개선과 구분한다.
4. 보완사진 추가는 기본 촬영 간격을 바꾸지 않고, 기본 첫 사진 교체는 새 시각에 따라 쌍을 재검증하는지 확인한다. 교체 취소·저장 실패에는 기존 상태가 유지되어야 한다.
5. 새 사진·새 차량·새 시설 선택 뒤 도착한 옛 분석이 현재 결과를 덮어쓰지 않는지 확인한다. 재시도는 실패 항목을 대상으로 하며 저장본이 중복 생성되지 않아야 한다.
6. 기존 형식 자료 읽기·변환 실패·저장 공간 부족·중단 후 재개·파생 이미지 중복·영상 프레임의 기본 쌍 오용을 검사한다. 실제 사진·API 키·서명 비밀은 Git에 넣지 않는다.
7. 웹과 iPhone의 구현·자동시험·빌드·화면 실행·실기기 촬영·실제 사진 판독 결과를 각각 기록한다. 아직 이 통합안의 구현이나 검증을 수행한 것은 아니다.

### 남은 범위 정리

공통 촬영 흐름은 확정되었다. 교차로 모퉁이, 전용구역 3개·기타의 구현 범위, 지도 공급자·GPS 초기 설정은 이 확정에 자동 포함하지 않는다. 아래 11절의 권장안으로 남은 범위를 정리한 뒤 원래 5번 사진 근거 중심 추천, 6번 확인 질문·선택 유지 계획으로 이어간다.

## 5. 4-1 소화전 — 확정 완료·구현 대기

확정일: 2026-10-13 (한국 시각). 사용자 발언:

> 소화전은 "이대로 확정"

확정 범위는 아래의 원본 보존·전체/부분 분석·시설 판독 분리·원본 근거 연결·부족 정보별 보완·거리 및 신고 조건 미확인 유지다. 웹과 iPhone에 같은 의미로 구현하고 실패·취소 시 기존 자료를 유지한다. 모델 교체나 추가 학습을 우선 도입하기로 확정한 것은 아니다. 타일 크기·호출 상한 등 세부값은 아래 검증을 거쳐 정할 구현 세부사항으로 남긴다. 사용자 동작이나 기능 범위를 바꿔야 하면 변경 이유를 기록하고 별도로 협의한다.

이 확정으로 다음 항목인 교차로 모퉁이 논의를 시작한다. 전체 계획이 끝나기 전 기능 구현을 시작하지 않는 진행 방식은 유지한다.

### 민원인에게 갖는 의미

차량 중심 사진의 작은 소화전을 전체 축소 분석에서 놓쳐 불필요하게 재촬영하는 일을 줄이는 것이 목표다. 원본에서 확인할 수 있는 정보를 먼저 활용하고, 부족한 부분만 구체적으로 촬영하도록 안내한다. 효과는 아직 측정하지 않았다.

### 확인한 현재 코드

- [웹 촬영](../src/lib/camera.ts): `getUserMedia`에 ideal 1920×1080을 요청하고 실제 영상 프레임을 JPEG로 저장한다. 기기에서 최대 사진 해상도가 확보된다는 의미는 아니다.
- [앨범](../src/lib/album.ts): 긴 변 최대 1920픽셀로 축소하고 워터마크를 적용한 결과를 저장한다. 가져온 원본 파일의 별도 보존 구조는 없다.
- [AI 입력](../src/lib/vision.ts): 사진을 최대 1280픽셀로 줄이고 최대 두 장을 판독 요청에 사용한다.
- [판독 API](../api/vision.ts): `fireHydrantNear`는 “소화전·소방용수시설 표시가 차 바로 옆에 보인다”는 관찰 항목이다. yes이면 hydrant 후보에 연결된다. 시설 종류·거리 검증은 분리되어 있지 않다.
- [유형 대조](../src/lib/crosscheck.ts): 유형 confidence 기준은 0.5다. 모델의 확신 점수를 실측 정확도 50%로 해석하지 않는다.
- 현재 iPhone은 AVFoundation 사진 저장 구조는 있으나 웹의 AI 판독 연결이 없다. 실제 사진 픽셀 크기·고해상도 설정·새 분석 연결을 별도로 구현·검증해야 한다.

소화전 본체의 형태·연결구·표지 문구 등을 확인하고 빨간 기둥·소화기·우체통 등 혼동 물체와 구분한다. 특정 색이나 본체 노출을 전국 공통 필수 조건으로 고정하지 않는다. 상세 사진은 시설 정체를 보완할 수 있지만 전경의 차량 연결이나 실제 거리를 자동 증명하지 않는다. 생성형 보정으로 만든 세부 형태·문구를 증거로 사용하지 않는다.

확정한 초기 접근은 같은 모델에서 입력·분석 구조의 효과를 비교하는 것이다. 학습이나 새 탐지 모델 도입은 아직 결정하지 않았다.

### 정해야 할 세부값과 검증

- 타일 크기·겹침·최대 분석 횟수, 전송량·시간 상한, 재시도와 중단 정책은 미정이다. 숫자를 성능 확인 없이 확정하지 않는다.
- 고해상도 촬영의 브라우저별 대체 경로, 원본 보존과 기존 데이터 호환, iPhone 모델 연결 방식은 구현 설계에서 구체화해야 한다.
- 같은 원본에 대해 기존 1280픽셀 전체 분석과 제안 방식의 비교를 수행한다. 단위시험과 실제 사진 정확도 시험을 구분한다.
- 소화전 오인식·놓침, 원본 내 대상 연결 오류, 근거 없는 거리 확정, 추가 촬영 요구, 지연·비용을 각각 측정한다. 현재 실측 결과와 확정 목표치는 없다.
- 시험 장면: 작은 소화전, 혼동 물체, 야간/역광/비, 가림, 관련 표시만 보임, 여러 차량, 멀리 있는 시설, 상세사진만 있음, 사진별 근거 상충.
- 실제 사진을 확보할 때 원본이나 개인정보를 Git에 넣지 않는다. 사진 확보 여부와 외부 분석 수행 여부를 구분해 기록한다.

### 논의에 사용한 근거

- [도로교통법 제32조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030974703): 관련 시설로부터 5m 기준. 시설 식별과 실제 거리 판단을 구분하기 위한 근거.
- [대전 동구 주민신고제 안내](https://www.donggu.go.kr/dg/kor/contents/235): 특정 표시로 소화전이 보이지 않는 경우도 안내. 이 지자체의 조건을 전국 규칙으로 복사하지 않는다.
- [SAHI 논문](https://arxiv.org/abs/2202.06934): 작은 물체의 분할 분석 연구. 해당 연구의 성능 수치를 국내 소화전·현재 모델의 성능으로 사용하지 않는다.
- [Gemini 이미지 이해 문서](https://ai.google.dev/gemini-api/docs/image-understanding): 이미지 분석 입력 관련 참고. 이번 개선에 어떤 설정을 사용할지는 별도 검증 대상.

## 6. 4-2 교차로 모퉁이 — 논의 중·미확정

2026-10-15 전용구역 3개 계획 수락 후 남은 기본 유형의 초안을 다시 구체화한다. 이번에 교차로 안이 확정된 것은 아니다. 기존 기본 구조를 유지하면서 보완사진의 장소 연결, 실제 거리 미확인, 사용자에게 보여줄 결과와 대표 가상 상황을 아래에 보강했다.

### 민원인에게 갖는 의미

차량 사진에서 교차로 구조가 잘렸거나 가려졌을 때, 무엇을 더 담아야 하는지 구체적으로 안내한다. 단순히 길이 휘거나 노란 선이 보인다는 이유로 유형을 확정하는 오류를 줄이는 것이 목표다. 아래는 다음 논의 초안이며 사용자 확정과 실제 구현은 아직 없다.

### 현재 코드와 개선할 판단 구조

[판독 API](../api/vision.ts)의 `intersectionCorner` 질문은 “차가 교차로 모퉁이(도로가 꺾이거나 만나는 곳)에 붙어 있다”이며 yes이면 corner 후보로 이어진다. [화면 유형명](../src/types/report.ts)은 이미 “교차로 모퉁이 5m 이내”다. 별도의 도로 연결 구조·가장자리 근거·표지/노면 상태·실제 거리 검증은 없다.

| 관찰 항목 | 제안하는 판독 기준 | 보류해야 할 경우 |
| --- | --- | --- |
| 도로 연결 구조 | 전체 사진에서 차도가 만나는 방향과 분기, T자·Y자·십자 등 관찰 가능한 형태를 기록 | 단순 굽은 길·건물 모서리·시설 진출입구를 모양만으로 교차로라고 확정하지 않음. 반대로 진출입구라는 이유만으로 법적 적용 제외도 자동 확정하지 않음 |
| 도로 경계·모퉁이 | 차도 가장자리·연석과 방향 변화 부분을 원본 내 후보 영역으로 표시 | 차량이나 화면 바깥으로 경계가 가려지면 임의로 이어 그려 법적 기준점으로 확정하지 않음 |
| 대상 차량 관계 | 선택된 차량이 어느 도로 가장자리·모퉁이와 연결되는지 확인 | 다른 차량이나 맞은편 모퉁이와 연결될 가능성, 원근으로 가까워 보이는 경우는 보류 |
| 표지·노면 | 해당 도로 가장자리의 주정차금지 표지, 선의 색·실선/점선·단선/복선 및 판독 가능 여부를 각각 기록 | 중앙선이나 주차구획선을 가장자리 규제선으로 오인하지 않음. 색만으로 유형 확정하지 않음 |
| 실제 거리 | 거리 근거와 미확인 상태를 별도 기록 | 일반 단안 사진의 픽셀 간격·차량 길이 가정·휴대폰 GPS만으로 5m 확정 금지 |

### 제안하는 분석·촬영 흐름

1. 전체 전경에서 도로의 연결 구조와 대상 차량을 먼저 분석한다. 소화전처럼 작은 부분만 잘라 보면 교차로 관계가 사라질 수 있으므로 전체 사진의 맥락을 유지한다.
2. 원본의 필요한 부분에서 도로 경계, 작은 표지, 흐린 노면 표시를 추가 판독한다. 각 결과를 원본 위치와 대상 차량에 다시 연결한다. 전체 장면과 부분 결과가 충돌하면 보류한다.
3. AI 응답을 도로 구조·경계/모퉁이 후보 영역·표지/노면·차량 연결·가림 사유·거리 확인 상태로 나눈다. 현재 하나의 `intersectionCorner` 응답보다 구체적인 부족 사유를 만들기 위한 변경이다.
4. 도로 구조가 안 보이면 “차량과 길이 만나는 부분이 함께 보이도록 전경을 추가해 주세요”, 작은 표지가 안 읽히면 표지 부분만 보완하도록 안내한다. 기존 사진의 재분석으로 해결되면 추가 촬영을 요구하지 않는다.
5. 기본 사진과 보완 전경을 구분한다. 보완사진 때문에 기본 시간 비교 사진의 위치·방향 조건을 충족했다고 간주하지 않으며, 기존 사진·수동 입력은 저장 성공 전까지 유지한다. 취소하면 기존 기록으로 돌아간다.
6. 결과는 “교차로 모퉁이 후보 / 도로 구조 확인 / 표지 또는 노면 확인 상태 / 거리·지역 조건 미확인”처럼 나눈다. 사진에서 유형 후보를 찾았다는 사실을 공식 접수 가능·위반 확정으로 표현하지 않는다.

### 검증과 미정 사항

- T자·Y자·십자 교차로, 둥근 모퉁이, 단순 굽은 길, 시설 진출입구, 주차장 내부 통로, 중앙선 혼동, 모퉁이 가림, 여러 차량, 야간·젖은 노면, 먼 차량이 가까워 보이는 장면을 포함해 시험한다.
- 교차로 구조 오인·놓침, 모퉁이와 대상 차량 연결 오류, 표지/노면 오인, 근거 없는 5m 확정, 불필요한 보완 촬영, 지연을 분리해 측정한다.
- 도로 구조 관찰과 법적 도로·교차로 해당 여부의 정답을 구분한다. 사진만으로 법적 성격을 확정할 수 없는 사례는 미확인으로 남긴다.
- 원본/부분 분석 기반은 소화전 확정안과 공유할 수 있지만, 교차로 판독 응답의 세부 형태·영역 표시 방식·기준값은 이 항목의 추가 논의 대상이다. 새 지도 정밀 측량, 거리 추정 모델 도입, 사용자 실측 요구는 이번 초안에 포함하지 않는다.
- 웹·iPhone 모두 같은 관찰 의미와 보완 동작을 목표로 하며 플랫폼별 구현·실행·실기기 검증을 분리한다. 현재 이번 항목의 기능 변경·시험은 미착수다.

### 2026-10-15 재협의: 사용자 흐름·오판 방지

**민원인에게 제안할 순서:** 대상 차량 선택 → 기존 전체 사진에서 도로 구조·모퉁이 후보 확인 → 원본의 필요한 표지/선 부분 확인 → 차량이 어느 도로 쪽·모퉁이와 연결되는지 대조 → 부족한 부분만 보완 → 거리·지역 조건 미확인 상태와 함께 저장.

도로가 만나는 구조, 굽은 도로, 건물 모서리, 시설 진출입구를 관찰상 구분한다. 신호등·횡단보도·노란 선이 없는 골목이라는 이유만으로 교차로 후보를 없애지 않는다. 반대로 단순 곡선이나 건물 코너만 보고 교차로로 확정하지 않는다. **도로교통법의 ‘도로의 모퉁이’와 사진상 교차로 구조를 동일한 한 값으로 합치지 않고**, 도로가 만나는 장면을 찾지 못했다는 이유로 법적 적용까지 자동 제외하지 않는다. 진출입구·주차장 통로의 법적 성격도 사진만으로 확정하지 않는다.

경계가 가려지면 화면 밖·차량 뒤의 선을 이어 그려 기준점을 만들지 않는다. 둥근 모퉁이를 임의의 한 점으로 정해 거리 계산에 쓰지 않는다. 여러 차량·모퉁이·갈림길은 각각 구별하고 대상 차량에 적용되는 연결을 확인한다. 맞은편의 선명한 모퉁이나 표지를 가까이 보인다는 이유로 가져오지 않는다.

다른 각도에서 추가한 전경은 차량·도로 구조·고정된 위치 특징·사진 시점을 대조해 연결한다. 같은 번호판이나 같은 GPS라는 이유만으로 같은 모퉁이에 계속 있었다고 판단하지 않는다. 보완 전경이 기본 시간 비교 사진이나 공식 촬영 방향 조건을 자동 대체하지 않는다. 나중에 찍은 다른 장소 사진 또는 원본을 자른 이미지를 독립 촬영으로 세지 않는다.

| 가상 장면 | 기존 사진에서 먼저 확인 | 필요할 때만 안내할 보완 / 남길 상태 |
| --- | --- | --- |
| 차량만 크게 보이고 갈림길은 사진 밖 | 다른 기본 사진과 원본 전체에서 도로 연결 확인 | “차량과 길이 만나는 부분이 함께 보이게 찍어 주세요.” |
| T자·Y자·골목이 만나지만 신호등·노면선이 없음 | 보이는 도로 연결 구조·경계·대상 차량 관계 | 구조가 충분하면 추가 전경 없음. 지역 표시 요건은 별도 확인 |
| 둥근 연석 옆에 차량이 있고 가장자리가 일부 가림 | 보이는 경계와 방향 변화, 전체 장면 | 연결 불명인 부분만 다른 각도. 실거리 미확인 유지 |
| 길은 휘지만 분기 여부가 안 보임 | 곡선 도로와 실제 연결 구조를 구별 | 사진상 구조 미확인. 법적 적용 제외로 단정하지 않음 |
| 건물 주차장 출입구 앞 차량 | 도로와 진출입구 구조, 표지, 차량 관계 | 필요 전경 또는 자료 확인. 출입구라는 이유만으로 법적 포함/제외 확정 금지 |
| 맞은편 모퉁이가 선명하고 대상 차량은 다른 쪽 | 차도·연석·교차부와 차량의 연결 | 대상 차량이 있는 쪽을 보여 주는 보완. 다른 모퉁이의 표지를 잘못 적용하지 않음 |
| 황색선은 보이지만 중앙선인지 가장자리인지 애매함 | 원본 전체에서 차로·연석과 선의 위치 확인 | 필요한 도로 맥락만 보완. 황색만으로 후보 확정 금지 |
| 사진상 차량과 모퉁이가 가까워 보임 | 실제 지상 위치의 연결·원근·거리 근거 | 5m는 미확인. 차량 길이·픽셀·휴대폰 위치로 통과시키지 않음 |

위 표는 **8개 문서 가상사례**이며 사진 AI 시험 결과가 아니다. 전체 사진에서 구조가 충분하면 표지 상세·다른 각도 사진을 모두 요구하지 않는다. 사진 부족, 법적 자료 미확인, 통신 오류를 분리한다. 실제 거리만 미확인이면 같은 전경을 반복 요청하지 않고 그 상태를 남긴다. 안전한 위치에서 촬영할 수 없거나 계속 가려지면 이유와 함께 저장하고, 차도로 이동하거나 직접 길이를 재도록 요구하지 않는다.

사용자 결과 예시는 **“교차로 모퉁이 후보 / 차량과 모퉁이 연결 확인 / 5m 이내 여부 미확인 / 지역 접수 조건 확인 필요”**다. 기존 유형명에 ‘5m 이내’가 포함돼 있다는 이유로 거리 점검을 통과시키지 않도록 거리 확인 상태를 함께 보여 준다. 기본 두 사진에서 차량이 보인 사실과 계속 정차·주차했다는 사실도 구분한다.

기술적으로 현재 `intersectionCorner` 한 응답을 도로 구조·가시 경계·표지/노면 종류·대상 연결·거리 상태·부족 사유로 나눈다. 각 관찰에는 원본 사진 ID·영역·대상·입력 버전을 붙이고, 대상 차량/사진 변경 후 옛 응답이 현재 결과를 덮어쓰지 않게 한다. 원본·주소·수동 본문 보존과 실패·취소·이어하기는 공통 확정안을 적용한다. iPhone에는 새 판독 연결이 필요하며 웹 기능이 이미 이식됐다고 표현하지 않는다. 지도는 주변 도로 맥락의 보조 자료이고 정밀 경계·실거리 인증 자료가 아니다.

수락 대상은 이 관찰 분리·원본 우선 보완·자료 보존·웹/iPhone 공통 의미와 기존 검증 계획이다. 실제 거리 측정이나 고정 정확도 약속을 새로 추가하지 않는다. 해당 안 수락 후 기타 범위·지도/GPS 공통 설정을 정리하고 원래 5·6번을 협의한다. 기능 구현은 전체 계획 확정 후 진행한다.

### 확인한 공식 근거 — 2026-10-13, 2026-10-15 재확인

- [도로교통법 제32조 제2호](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030974703)는 교차로의 가장자리나 도로의 모퉁이로부터 5m 이내를 정차·주차 금지 장소로 정한다. 법적 거리 기준과 사진상 형태 인식을 구분한다.
- [춘천시 주민신고제 안내](https://www.chuncheon.go.kr/traffic/crackdown/parking-violation/report/)는 표지 또는 노면표시가 설치된 도로의 해당 구간을 안내한다. 이 지자체의 신고 조건을 전국 자동 규칙으로 적용하지 않고 관할별 자료를 확인한다.

## 7. 4-3 버스정류소 — 촬영 방향·정류소 선정·사진 근거·보완 촬영 확정

### 민원인에게 갖는 의미

작게 나온 정류소 표시를 원본에서 먼저 확인하고, 정류소와 신고하려는 차량의 관계가 부족할 때만 필요한 사진을 안내한다. 길 건너 정류소나 단순 대기시설 때문에 잘못된 유형을 추천하는 일을 줄이는 것이 목표다. 촬영 방향 기능, 주변 정류소 선정안, 사진 근거 확인·보완 촬영안은 2026-10-14에 각각 확정되었다. 아래 거리·위치정보 검토 중 GPS 숫자 기준·지도 공급자 등 공통 설정은 미확정으로 남긴다. 기능 구현·정확도 측정은 아직 없다.

### 확인한 현재 코드

- [판독 API](../api/vision.ts)는 `busStopVisible`에 “버스정류장 표지판·승강장이 차 바로 옆에 보인다”를 묻고 yes이면 busstop 후보로 연결한다. 정류소 식별, 대상 차량과의 관계, 정차구획, 실제 거리를 별도 항목으로 확인하지 않는다.
- [좌표 추천](../src/lib/recommend.ts)은 가장 가까운 정류소 하나의 좌표 거리와 GPS 오차를 10m 기준에 대조해 가능/유력 후보를 만든다. 현재도 법적 판정이 아닌 추천이지만, 이 거리는 차량과 정류소 표시 사이의 실측 거리가 아니다.
- [주변 시설 자료](../src/lib/facilities.ts)는 API와 격자 자료를 합친다. 데이터 없음·일부 누락·조회 실패 상태가 이미 있다. 자료의 정류소 점이 현장의 표지·정차구획 기준점과 일치한다거나 어느 도로 쪽인지 보증하지 않는다.
- [유형 이름](../src/types/report.ts)은 “버스정류소 10m 이내”다. 이 이름이 사진으로 10m 이내를 확인했다는 표시로 읽히지 않도록 후보 상태와 거리 확인 상태를 분리할 필요가 있다.

### 제안하는 판단 기준과 기술적 변경

| 확인할 내용 | 개선안 | 보류하거나 구분할 상황 |
| --- | --- | --- |
| 정류소 식별 | 기둥·표지의 버스 표시, 정류소 명칭·번호·노선 안내, 승강장과 정류소 노면표시를 각각 관찰 | 지붕·의자·광고판만으로 확정하지 않음. 지붕 없는 기둥형 정류소도 후보로 인정. 모든 문구가 읽혀야만 인식되도록 강제하지 않음 |
| 작은 표시 | 전체 장면과 원본의 표지 부분을 함께 분석하고 판독 문구·위치를 원본에 연결 | 흐린 문구를 생성하거나 추측해 채우지 않음. 표지 사진만으로 차량과의 연결을 확정하지 않음 |
| 대상 차량과 정류소의 관계 | 선택 차량, 도로 가장자리·차로·중앙분리대, 정류소의 위치 관계를 관찰 | 맞은편 정류소나 다른 차량과 잘못 연결하지 않음. 중앙차로·방향·가림이 불명확하면 보류하며 반대편이라는 이유만으로 법적 적용 제외도 자동 확정하지 않음 |
| 정차구획 | 버스 정차구획의 경계와 대상 차량이 걸친 것으로 보이는 영역을 따로 기록 | 버스전용차로의 선·일반 황색선·주차구획선을 정류소 정차구획으로 오인하지 않음. 사진상 겹침을 곧바로 위반 확정으로 바꾸지 않음 |
| 시설 자료 대조 | 가까운 정류소 여러 후보를 남기고, 읽힌 명칭·번호와 도로 쪽 등 확인 가능한 단서로 대조 | 데이터 내부 ID를 현장 정류소 번호로 취급하지 않음. 이름이 같은 반대편 정류소, 자료 누락·오래된 위치·사진과의 상충을 미확인으로 유지 |
| 거리와 결과 | 촬영 위치 기준 참고 거리와 차량의 실제 거리 확인 상태를 분리 | GPS 오차가 작아도 차량 위치나 법적 기준점을 확보한 것은 아님. 사진 픽셀·차량 길이 가정·휴대폰 GPS만으로 10m 이내 확정 금지 |

현재 한 개의 `busStopVisible` 응답을 정류소 식별 근거, 표지 문구·영역, 정차구획 영역, 대상 차량 연결, 가림·흐림 사유로 나누는 것이 핵심 변경이다. 서버와 클라이언트의 응답 검증·저장 형식도 함께 바꿔야 한다. 사진 관찰과 시설 자료 대조, 실제 거리, 지역 조건의 상태를 분리하며 AI가 답한 숫자나 확신 점수만으로 미확인 상태를 해제하지 않는다.

시설 자료 대조는 보조 근거다. 전체 유형 간 우선순위와 추천 점수 변경은 뒤의 5번에서 협의한다. 사용자의 확인 질문과 수동 선택 유지에 관한 전체 동작은 6번에서 협의하며, 사용자 확인을 사진 인식 성공이나 법적 거리 증명으로 저장하지 않는다.

### 제안하는 분석·촬영 흐름

1. 기존 전체 사진에서 대상 차량·정류소 후보·도로 쪽·정차구획을 확인한다. 여러 차량 중 대상이 불명확하면 임의 차량에 근거를 붙이지 않는다.
2. 정류소 표시가 작으면 보존된 원본의 해당 부분을 다시 분석한다. 소화전 확정안의 원본·부분 분석 및 출처 연결 구조를 공유한다. 같은 원본에서 자른 사진은 별도 촬영본으로 세지 않는다.
3. 원본에서 해결되지 않은 정보에 따라 다음처럼 구체적으로 안내한다. 아래 안내는 예시 문구다.
   - 정류소 표시를 식별할 수 없음: “정류소 표지가 더 잘 보이도록 찍어 주세요.”
   - 차량과 정류소의 위치 관계가 안 보임: “차량과 정류소 표지가 한 화면에 보이도록 찍어 주세요.”
   - 정차구획과 차량의 관계가 가려짐: “차량과 정류소 바닥 표시가 함께 보이도록 찍어 주세요.”
4. 이미 충분히 보이는 정보를 다시 요구하지 않는다. 상세사진과 전경사진을 매번 모두 찍도록 강제하지 않는다. 표지가 식별되지만 이름만 안 읽히는 경우에는 이름 촬영을 무조건 요구하지 않는다.
5. 결과는 “정류소 표시 확인 / 차량과의 위치 관계 확인 필요 / 실제 10m 이내 여부 미확인”처럼 확인된 부분과 부족한 부분을 구분한다. 보완사진으로도 실제 거리를 확인하지 못하면 미확인 상태를 유지한다.
6. 기본 시간 비교 사진과 보완사진의 역할을 유지한다. 기본 사진에 필요한 정보가 빠진 경우 보완사진만으로 공식 촬영 요건이 충족됐다고 처리하지 않는다. 취소·통신 실패·늦은 분석 결과·저장 실패 때 기존 사진·주소·수동 내용을 보존한다.

대상 차량이 버스인 경우 외형만으로 정상 승하차 또는 위반을 자동 확정하지 않는다. 운행노선·시간·승하차 상황 등 예외 적용에 필요한 사실은 사진만으로 확인되지 않을 수 있다. 이 초안은 정류소 유형의 근거를 정리하는 기능이며 법적 위반 판정을 자동화하는 안이 아니다.

- 교체 사진은 저장 성공 전까지 기존 사진을 유지한다. 기존 주소·수동 본문·선택한 대상 차량/정류소도 성공한 명시적 변경 없이 덮어쓰지 않는다. 취소·통신 실패·저장 실패 뒤 재시도할 수 있게 한다.
- 사진이나 대상 차량·정류소 선택이 바뀌면 이전 분석의 연결 상태를 재검토한다. 늦게 도착한 옛 요청 결과가 새 선택을 덮어쓰지 않도록 요청 ID·분석 대상 버전을 확인한다.
- 사용자가 추가 촬영을 할 수 없으면 기존 자료와 미확인 사유를 저장해 나중에 이어갈 수 있게 한다. 사용자의 확인 응답을 AI 판독 성공이나 실제 거리 증명으로 바꾸지 않는다. 결과는 확인한 항목과 남은 항목을 함께 보여준다.
- 웹과 iPhone에 같은 사진 역할·판독 상태·보완 안내·취소 의미를 적용한다. iPhone의 AI 연결은 신규 작업으로 따로 구현·검증한다. 원본·개인정보는 Git에 넣지 않는다.

[Apple ARKit sceneDepth](https://developer.apple.com/documentation/arkit/arconfiguration/framesemantics-swift.struct/scenedepth)는 LiDAR 지원 기기의 깊이 정보와 지원 여부 확인을 안내한다. 두 자료는 이 앱에서 정류소 거리 정확도를 검증했다는 근거가 아니다.

### 위치정보로 정확도를 높이는 후속 제안 — 2026-10-14, 미확정

사용자 제약·질문: “현장검증을 직접적으로 하긴 어려운데, 위치정보를 기반으로 정확도를 높이는 방법은 없는지 생각해보고 대답”. 직접 현장 검증을 전제로 하지 않는 개선과 검증 방법을 우선 검토한다. 이 발언은 버스정류소 초안이나 새 측정 기능의 확정이 아니다.

**제안 목표:** 위치정보를 사진과 결합해 잘못된 정류소를 고르는 오류를 줄이고, 근거가 부족한 결과를 보류한다. 현장 시험 없이 차량의 실제 10m 안/밖 판독 정확도나 개선율을 보장하지 않는다.

#### 추가로 확인한 현재 구조

- [촬영 화면](../src/components/CaptureFlow.tsx)은 이미 `watchPosition`과 `enableHighAccuracy: true`를 사용한다. 따라서 고정밀 요청이나 반복 수신 자체를 새 개선으로 설명하지 않는다. 현재는 마지막 수신 좌표·accuracy를 `pos`에 덮어쓰며 위치 취득 시각과 최근 값의 변동 이력을 이 상태에 남기지 않는다.
- [정류소 API](../api/stops.ts)는 응답을 내부 ID·이름·위경도로 축약한다. 현장에 적힌 공개 정류소 번호와 제공기관·자료 기준일·좌표 품질을 구분해 보관하는 구조가 없다. [시설 자료 병합](../src/lib/facilities.ts)은 두 점이 3m 이내라는 이유로 중복을 합치며, 격자 자료의 ID는 내부 생성값이다.
- [거리 계산](../src/lib/geo.ts)의 `isDecisive`는 주어진 accuracy 구간을 경계 판단에 사용한다. 단말이 보고한 accuracy는 확률적 위치 품질 정보이며, 절대 오차 상한이나 차량 위치의 오차가 아니다. 같은 의미의 무조건 확정 조건을 새 차량 거리 판단에 재사용하지 않는다.

#### 우선 제안하는 공통 개선

1. **위치 취득 시각·품질·흔들림 확인:** 촬영 직전의 짧은 수신 구간에서 취득 시각, 보고 정확도, 좌표 변화와 오래된/반복된 값을 확인한다. 이상값에 덜 민감한 대표값을 비교 검토하되 이동 중인 사용자의 서로 다른 위치를 한 점으로 평균내지 않는다. 화면을 오래 기다리게 하거나 사진 촬영을 막지 않으며 품질이 부족하면 위치 기반 추천만 약하게 한다. 수신 기간·샘플 수·기준값은 미정이다. 반복 측정으로 공통 편향이 사라지거나 측정 수만큼 오차가 줄어든다고 가정하지 않는다.
2. **정류소 여러 후보 유지:** 촬영 위치 주변의 후보를 모으고 GPS 오차·자료 누락·조회 범위를 함께 관리한다. 가장 가까운 하나를 곧바로 해당 정류소로 선택하지 않는다. 자료가 없거나 GPS 품질이 나쁘면 사진 근거를 취소하지 않는다. 검색 반경은 차량의 10m 조건과 구분하며, 포함된 후보가 곧 차량 가까이에 있다는 뜻은 아니다.
3. **사진 속 공개 번호·이름과 대조:** 읽힌 정류소 번호를 해당 지역·제공기관의 번호 체계에 맞춰 후보 자료와 대조한다. 공개 번호와 내부 ID를 구분하고 앞자리 0을 보존한다. 번호가 없으면 이름·노선·도로 쪽 등 실제 확보된 단서를 함께 사용하되 이름 하나만으로 맞은편 정류소를 합치지 않는다. 사진 OCR이 모호하면 지도에 맞춰 글자를 추측하지 않고 불일치·미확인으로 남긴다. 사용자에게 번호를 필수 입력하게 하거나 번호가 안 읽힌다는 이유만으로 촬영 실패 처리하지 않는다.
4. **출처와 최신성 관리:** 정류소의 제공기관·공개 번호/내부 ID·좌표계·자료 기준일·조회일·사진 연결 근거를 보존한다. 다른 출처에서 3m 안에 있다는 이유만으로 같은 정류소로 합치는 방식을 보완한다. 현재 API를 조회했다는 사실과 시설 좌표가 현장에서 갱신됐다는 사실을 구분한다. 원천을 공유하는 여러 자료의 일치를 독립적인 정확도 검증으로 세지 않는다.
5. **근거별 결과 표시:** “사진 속 정류소 번호와 주변 자료 일치”, “차량과 정류소의 위치 관계 확인 필요”, “실제 거리 미확인”을 나누어 표시한다. 계산한 거리는 촬영 위치 기준인지 사용자가 지정한 위치 기준인지 명시한다. 검증하지 않은 ‘정확도 95%’ 같은 점수를 생성하지 않는다. 전체 유형의 추천 순위 변경은 5번 협의에 연결한다.

#### 선택적으로 검토할 보완

- **지도에서 차량 위치 지정:** 후보가 계속 모호할 때 사용자가 정류소 또는 차량이 있는 도로 쪽·대략의 위치를 선택하도록 할 수 있다. 촬영자의 GPS와 차량 위치를 혼동하지 않도록 `사용자 지정 위치`로 따로 저장하고 원래 사진 좌표·주소·수동 내용을 덮어쓰지 않는다. 지도 클릭은 실측 좌표가 아니며 정류소 점·지도 배경·사용자 선택에도 오차가 있다. 차량 위치와 기준점의 품질을 확보하지 못하면 10m 경계 확정에 쓰지 않는다. 기본 촬영의 필수 단계로 추가하지 않으며 구체적 사용자 질문은 6번에서 협의한다.
- **촬영 방향 활용:** 나침반·기기 자세에서 카메라 방향을 올바르게 계산할 수 있는 경우에만 후보 대조를 보조한다. 웹 Geolocation의 `heading`은 이동 방향이므로 카메라가 바라보는 방향으로 쓰지 않는다. 기기 방향 보정·센서 오차·권한·지원 여부를 처리해야 하고, 방향만으로 대상 차량 거리를 구할 수는 없다. 현장 검증이 어려운 현재 조건에서는 필수 근거로 두지 않는 안을 제안한다.
- AR/LiDAR 측정, 두 위치의 촬영 방향을 이용한 삼각측량, 정밀 지도에 의한 실제 거리 확정은 우선 공통 개선에 추가하지 않는다. 특히 기본 사진을 위해 이동 촬영을 요구하는 방식으로 기존 촬영 조건을 바꾸지 않는다.

#### 현장에 가지 않고 할 수 있는 검증과 그 한계

- 공개 정류소 자료의 번호·좌표·자료 시점·좌표계, 중복·결측·동명이름 후보를 검사한다. 실제 API 필드와 지역별 번호의 연결 가능성은 구현 전에 샘플로 확인한다. 이번 조사에서는 공식 설명과 기존 코드를 확인했으며 전체 자료 다운로드나 인증 API 호출은 수행하지 않았다.
- 알려진 좌표와 식별자를 가진 사례에 GPS 흔들림·고정 편향·오래된 위치·수신 중단·이동·도로 양쪽 후보·동명 정류소·번호 판독 오류를 주입해 기존 최근접 방식과 새 후보 대조 방식을 비교한다. 만드는 자료와 평가 자료를 나누며 임계값을 맞춘 사례만 성과로 보고하지 않는다.
- 평가 항목은 시뮬레이션 조건에서의 잘못된 정류소 선택, 정답 후보 누락, 모호할 때 보류 여부, 불필요한 질문, 기존 사진/입력 보존이다. 실제 촬영자의 GPS 정밀도나 실제 사진 판독 정확도를 이 결과로 대체하지 않는다. 사용 가능한 적법한 기존 사진이 있을 때에만 사진 판독 비교를 추가하고 자료 조건을 기록한다.
- 웹·iPhone의 같은 입력에 대한 결과·실패/취소 동작을 각각 확인한다. iPhone 센서 연결과 실제 기기 정확도 검증이 남아 있으면 별도 미검증으로 보고한다. 현장 검증이 불가능하다는 이유로 구현 가능한 공통 개선까지 중단하지 않는다.

### GPS 품질·카카오/네이버 지도 상세 계획 — 2026-10-14, 촬영 방향·정류소 선정 부분 확정

사용자가 GPS 품질 확인 방법부터 순서대로 검토하고 지도에서 내 위치와 정류소를 확인하는 구현 계획을 요청했다. [GPS 품질 확인·지도 위치 계획](gps-map-location-plan-2026-10-14.md)에 기존 지도 코드, 두 공급자의 공식 SDK 가능 범위, 위치 취득 시각·보고 오차·일관성 검사, 현재/촬영/차량 위치 구분, 저장·취소, 양쪽 플랫폼 구현 순서와 비현장 검증을 구체화했다.

해당 문서의 5초·10초·20m·50m 등은 상태 분류를 시험할 초기 설정 초안이며 측정 성능이나 법적 거리 판정 기준이 아니다. 카카오 우선 연결도 기존 주소 API 경로를 고려한 권장안일 뿐 확정하지 않았다. 기존 ‘위치 초기화’가 새 GPS 측정이 아닌 촬영 원점 복귀이며 지도 선택 좌표가 주소로만 저장되는 점을 개선 대상으로 확인했다. 계획 수립 요청을 전체 기능 구현 승인이나 버스정류소 안의 확정으로 처리하지 않는다.

**2026-10-14 사용자 확정: "이대로 확정".** 직전 설명의 촬영 방향 표시·사진별 위치/방향/취득 시각 저장·품질에 따른 정류소 방위 대조·센서 미지원 시 기존 기능 유지 범위를 확정했다. 웹·iPhone 구현 대기로 두고, 지도 공급자·GPS 숫자 기준·버스정류소 전체 안은 자동 확정하지 않는다.

**이어서 2026-10-14 사용자 확정: "정류소 선정안도 이대로 확정. 다음 진행해봐."** 주변 여러 정류소 후보 수집, 사진 공개 번호 우선 대조, 이름·노선·위치·방향 보조, 추천 이유 표시, 상충 시 보류와 필요 시 사용자 선택을 확정했다. 상세 계획의 정류소 선정안을 구현 대기로 바꾸고, 다음 협의로 사진 근거 확인·부족한 부분만 보완 촬영안을 기록했다.

**이후 2026-10-14 사용자 확정: "사진 근거 확인이랑 보완 촬영안도 이대로 확정. 다음 진행해봐."** 위 사진 근거·보완 촬영 세부안도 구현 대기로 전환했다. 지도 공급자·GPS 숫자 기준은 공통 설정 협의로 남기고, 다음 기본 유형인 횡단보도로 진행한다.

- [춘천시 주민신고제 안내](https://www.chuncheon.go.kr/traffic/crackdown/parking-violation/report/): 정류소 표지 주변 거리와 버스 노면표시 침범을 안내한다. 이 지역의 접수 기준을 전국 규칙으로 복사하지 않는다. 공식 앱 촬영·동일 위치/방향 등 별도 요건도 있으므로 시제품 사진 분석 성공을 공식 접수 요건 충족으로 표현하지 않는다.

## 8. 4-4 횡단보도 — 확정 완료·구현 대기

2026-10-14 버스정류소 사진 근거·보완 촬영안 확정 후 제안한 다음 유형이다. 목표는 횡단보도가 사진에 보이는 사실과 대상 차량이 그 위에 걸쳐 보이는 사실을 나누고, 관계가 불명확할 때 필요한 사진만 보완하도록 하는 것이다.

**2026-10-14 사용자 확정: "이대로 진행".** 직전 횡단보도 개선안을 수락한 발언으로 기록한다. 아래 횡단보도 식별·대상 차량 연결·위치 관계·정지선 분리, 원본 재분석과 필요한 보완, 지도 보조·지역 기준 구분, 자료 보존·웹/iPhone 검증 계획을 확정하고 구현 대기로 전환한다. 다음 협의 유형은 어린이보호구역이다. 전체 계획 확정 후 구현하는 순서를 유지하며 기능 구현·빌드·실기기 검증·인식 정확도 측정은 미착수다.

### 현재 분석에서 바꿀 부분

- [판독 API](../api/vision.ts)는 `onCrosswalk`에 차량이 횡단보도 위에 걸쳐 있는지를 한 번에 묻고 `yes/no/unclear`로 답하게 한다. 번호판·차량·횡단보도 근거 상자는 있으나, 횡단보도 식별·차량 연결·보이는 경계·겹침 사유·정지선 여부가 별도 항목으로 나뉘어 있지 않다.
- [교차 점검 안내](../src/lib/crosscheck.ts)는 흰 줄무늬와 차 바퀴가 보이도록 안내한다. 이를 필요한 관계에 따라 차량 앞부분/옆부분과 횡단보도 경계를 함께 보여 달라는 구체적인 안내로 개선한다. 바퀴가 흰 페인트를 밟았는지만 필수 조건으로 삼지 않는다.
- [시설 추천](../src/lib/recommend.ts)은 횡단보도 중심점과 촬영 좌표의 거리로 가능 후보를 제시한다. 현재 15m 설정은 후보 검색용이며 횡단보도 경계나 법적 거리 확인값이 아니다. 위치와 촬영 방향은 주변 후보를 찾는 보조 근거로 쓰고 사진 속 침범을 증명하는 근거로 쓰지 않는다.

### 확인할 사진 근거

| 항목 | 제안하는 확인 내용 | 불명확할 때의 처리 |
| --- | --- | --- |
| 횡단보도 식별 | 도로를 건너는 줄무늬의 배열·범위, 연결된 보행 공간 등 주변 맥락 | 흰 선 하나, 정지선, 주차구획, 안전지대 빗금, 과속방지턱 무늬와 구분이 어려우면 보류. 고원식 횡단보도 가능성도 고려해 턱이 있다는 이유만으로 배제하지 않음 |
| 대상 차량 연결 | 어느 차량에 대한 분석인지 번호판·차량 영역·사진 ID를 연결 | 여러 차량 중 대상이 모호하면 사진에서 지정. 사용자 지정 자체는 번호판 판독 성공으로 처리하지 않음 |
| 차량과 횡단보도의 관계 | 보이는 횡단보도 경계와 차량 바퀴·차체 끝부분을 전체 도로 맥락에서 함께 확인 | 원근 때문에 상자만 겹치거나 경계가 가려졌다면 미확인. 흰 줄 사이 빈 부분도 포함한 횡단보도 범위를 살피되 가려진 경계를 관찰 사실로 생성하지 않음 |
| 정지선과의 관계 | 횡단보도 앞 정지선의 식별, 대상 차량과의 관계를 별도 기록 | 정지선만 넘은 것으로 보이는 장면을 횡단보도 위라고 기록하지 않음. 해당 지역 기준 확인과 연결 |

차체 앞부분이 걸쳐 보이는 장면도 관찰 대상으로 남기며 “바퀴가 선을 안 밟았으므로 해당 없음”으로 자동 배제하지 않는다. 반대로 사진의 차량 상자와 횡단보도 상자가 겹쳤다는 이유만으로 침범 확인 상태로 바꾸지 않는다. 상자는 확인할 영역을 안내하는 자료이며 실제 지면의 점유 영역을 정확히 측정한 결과가 아니다.

각 관찰에 원본 사진 ID·대상 차량·해당 영역·사유를 연결한다. 충분한 근거, 관계 불명확, 해당 사진에서 근거를 찾지 못함, 분석 실패를 구분한다. 원본의 필요한 부분을 다시 확인할 때 전체 화면도 함께 사용한다. 확대나 잘라내기가 원본에 없는 정보를 만들어 주는 것으로 설명하지 않는다.

### 원본 재확인 뒤 필요한 사진만 안내

| 현재 상태 | 먼저 할 일 | 그래도 필요한 경우의 보완 안내 |
| --- | --- | --- |
| 횡단보도가 작거나 흐림 | 원본에서 표시 배열·주변 도로를 함께 재확인 | “차량과 횡단보도 줄무늬가 함께 잘 보이도록 찍어 주세요.” |
| 횡단보도는 보이지만 차량이 걸쳤는지 불분명 | 경계와 차량 끝부분이 보이는 기존 사진을 확인 | “차량 앞부분과 횡단보도가 시작되는 부분이 함께 보이도록 찍어 주세요.” 등 실제 부족한 부위에 맞춰 안내 |
| 차량이 경계를 가림 | 기존 다른 사진에 관계 근거가 있는지 확인 | 안전한 보행 공간에서 관계가 더 보이는 사진을 보완할 수 있을 때만 안내. 어려우면 미확인 사유와 기존 자료를 저장 |
| 정지선만 보임 | 횡단보도와 정지선의 구별, 대상 차량의 관계 재확인 | 횡단보도 판단이 더 필요한 경우에만 주변 범위를 넓힌 사진 안내. 정지선 자체로 충분한 지역 기준이 확인됐다면 무조건 재촬영 요구하지 않음 |
| 기본 사진 번호판이 읽히지 않음 | 원본 번호판 분석 경로로 확인 | 해당 기본 사진 보완 안내. 횡단보도 상세사진으로 번호판 요건을 채운 것으로 처리하지 않음 |
| 차량·횡단보도·관계가 충분히 보임 | 기존 사진을 근거로 사용 | 추가 촬영 요구하지 않음 |
| 통신·분석 요청 실패 | 기존 사진으로 재시도 또는 나중에 분석 | 사진 부족으로 분류하지 않음 |

한 사진으로 여러 부족한 근거가 해결되면 추가 촬영을 합친다. 보완을 위해 새로운 각도의 사진을 찍더라도 기본 시간 비교 사진의 촬영 조건을 충족한 것으로 자동 처리하지 않는다. 원본 잘라내기·보완사진으로 기본 두 장을 대신하거나 시간 계산을 초기화하지 않는다. 각 기본 사진에 필요한 근거가 있는지도 따로 유지한다.

기존 사진·주소·사용자 본문·수동 선택은 교체 저장 성공 전까지 보존한다. 취소·저장 실패 후에도 다시 이어갈 수 있어야 한다. 대상 차량이나 사진 변경 후 늦게 도착한 옛 분석은 새 결과를 덮어쓰지 않는다. 이 동작은 앞서 확정한 보존·사진 역할 원칙을 횡단보도에도 적용하는 제안이다.

### 지도·방향·지역 기준의 역할

GPS와 방향의 품질이 확보되면 어느 도로의 횡단보도인지 후보를 좁히는 데 참고한다. 현재 자료에는 중심점만 있으므로 지도에서 가까워 보인다는 이유로 차량이 횡단보도 안에 있다고 처리하지 않는다. 지도 자료가 없거나 방향을 못 받더라도 사진 근거를 분석할 수 있어야 한다. 촬영자 위치와 차량 위치를 혼동하지 않으며 사진이나 지도 중심점으로 정밀한 실제 거리를 계산했다고 표시하지 않는다.

사진상 횡단보도 점유 근거와 법령·지역 접수 기준을 분리한다. 횡단보도 위가 아니라는 관찰을 합법 판정으로 바꾸지 않는다. 도로교통법은 횡단보도 자체 외에 주변 거리 규정도 두고 있으며, 춘천시 주민신고제는 정지선 침범도 안내한다. 후자의 지역 기준을 전국 공통으로 복사하지 않는다. 지역이 불분명하거나 최신 기준을 확인하지 못하면 확인 필요로 표시하고 공식 안내의 출처·확인일을 보존한다.

사진 한 장으로 정지 지속 시간이나 신호 대기·위험방지 등 정차 사유를 확정하지 않는다. 이 단계는 사진 근거를 정리하는 시제품 기능이며 공식 신고 수용이나 과태료 부과 결과를 판정하지 않는다.

### 기술 변화와 검증 계획

1. 단일 `onCrosswalk` 응답을 횡단보도 식별·대상 차량 연결·위치 관계·정지선 관찰 및 불명확 사유로 확장한다. 기존 화면·추천과 연결하는 호환 처리를 두며, 응답 항목 증가 자체를 인식 성능 향상 실적으로 보고하지 않는다.
2. 전체 사진과 필요한 원본 부분의 분석 결과를 같은 원본에 연결한다. 처음에는 기존 모델에 구조화된 확인 항목·재분석 절차를 적용하며, 새 학습 모델·정밀 지면 투영·픽셀 단위 분할 성능을 이미 확보한 것으로 전제하지 않는다.
3. 관찰 근거로 부족 사유를 만들고 필요한 촬영 안내를 고른다. 차량의 수동 선택은 사용자 입력으로 보존하고 AI 인식 사실과 구분한다. 유형 추천의 우선순위·확인 질문 전체 흐름은 후속 5·6번에서 함께 정리한다.
4. 웹과 iPhone에 같은 의미의 관찰 항목·사진 역할·안내·미확인 상태·실패/취소 동작을 구현한다. iPhone의 신규 AI 연결은 별도 작업으로 기록한다.
5. 시험용 응답으로 상태 전환과 보존을 검증한다. 사진상 단순 겹침, 흰 줄 사이에 있는 바퀴, 차체 앞부분만 걸친 모습, 가려진 경계, 여러 차량/횡단보도, 정지선만 보임, 닳은 표시·야간·젖은 노면, 지도 누락·상충, 통신 실패를 포함한다.
6. 사용할 권한이 있는 사진을 확보하면 실제 모델의 횡단보도 오인·놓침, 차량 연결 오류, 관계 오판, 불필요한 보완 촬영 요구, 처리 시간·비용을 현재 방식과 비교한다. 정답 관계를 확인하기 어려운 사진은 불명확으로 분리한다. 모의 응답 시험·빌드 성공과 실제 이미지 정확도·실기기 검증을 따로 보고한다. 현재 측정값이나 보장하는 정확도 수치는 없다.

### 확인한 공식 근거 — 2026-10-14

- [도로교통법 제32조 제1호·제5호](https://law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1020822435), 확인 시 시행일 2026-10-13: 횡단보도와 주변 10m의 주정차 금지 규정, 조문 단서의 예외. 사진의 점유 관찰과 전체 법적 판단을 분리하는 근거다.
- [춘천시 주민신고제 안내](https://www.chuncheon.go.kr/traffic/crackdown/parking-violation/report/): 횡단보도 위·정지선 침범에 대한 지역 안내와 공식 앱 사진·촬영 간격·위치/방향 등 접수 요건. 전국에 동일하게 적용된다고 전제하지 않는다.

## 9. 4-5 어린이보호구역 — 확정 완료·구현 대기

2026-10-14 횡단보도 안 확정 후 제안한 다음 유형이다. 목표는 주변에 학교가 있거나 색칠된 도로가 보이는 경우와 대상 차량이 실제 어린이보호구역 도로에 있는 것으로 확인되는 경우를 구분하는 것이다. 보호구역을 알아보는 사진 분석과 해당 지역 주민신고제의 대상 구간·시간 안내도 분리한다.

**2026-10-14 사용자 확정: "어린이보호구역도 이대로 확정. 다음 인도 유형 진행해봐."** 아래 표시 식별·차량 도로 관계·공식 지정 자료·지역 주민신고제 대상/시간 조건 분리, 원본 재분석 후 필요한 보완, 자료 보존·웹/iPhone 검증 계획을 확정하고 구현 대기로 전환한다. 다음 협의 유형은 인도다. 전체 계획 확정 후 함께 구현하는 순서를 유지하며 기능 구현·빌드·실기기 촬영·실제 인식 정확도 검증은 미착수다.

### 현재 코드와 바꿀 부분

- [판독 API](../api/vision.ts)의 `schoolZoneMarking`은 빨간 노면, 어린이보호구역 표지·글씨가 보이는지를 한 항목으로 묻는다. 관찰이 `yes`이면 보호구역 유형 후보에 연결한다. 표시 종류·문구·시작/끝·대상 차량 도로와의 관계가 분리되어 있지 않다.
- [촬영 안내](../src/lib/crosscheck.ts)는 빨간 노면이나 보호구역 표지가 나오도록 한다. 앞으로 색상만 찾도록 유도하지 않고 어린이보호구역을 식별할 표시와 대상 차량의 관계 중 부족한 부분을 안내한다.
- [시설 추천](../src/lib/recommend.ts)은 가장 가까운 시설 좌표에서 300m 이내면 가능 후보로 제시한다. 확정 판단을 하는 코드는 아니지만, 가장 가까운 한 시설·고정 반경으로는 실제 지정 도로와 다른 후보를 구분하기 어렵다. 후보 수집 범위와 지정 구역 경계를 다른 값으로 다룬다.
- [시설 수집](../scripts/collect_facilities.py)과 [조회](../src/lib/facilities.ts)는 학교 등 대상시설의 위도·경도·이름을 저장한다. 지역 필터는 서울·전북 계열 명칭이며, 이 점 자료를 전국 보호구역의 정확한 경계 자료로 취급하지 않는다. 출처별 범위·기준일·지정 상태를 판별할 정보를 보존하도록 확장한다.
- [지역 규칙](../src/lib/localRules.ts)에는 유형별 시간·지역 출처·확인일이 이미 있다. 다만 현재 시간 함수는 공휴일을 판단하지 않으며, 표준 시간과 일부 지역 예외를 합친 결과를 '단속' 시간으로 표현한다. 보호구역 인식, 주민신고제 적용 시간, 법적 금지 여부, 과태료 안내를 서로 혼동하지 않도록 데이터 의미와 안내 문구를 정리한다.

### 사진에서 확인할 항목

| 항목 | 제안하는 확인 내용 | 단독으로 확정하지 않을 단서 |
| --- | --- | --- |
| 어린이보호구역 표시 | 공식 표지의 형태·어린이보호구역 문구·노면 글씨를 주변 도로와 함께 확인 | 빨간/노란 포장, 숫자 30, 학교 건물이나 간판만 보임. 노인·장애인 보호구역 문구와도 구분 |
| 표시의 의미 | 읽을 수 있는 시작·끝·방향·거리 안내를 각각 기록 | 표지가 보인다는 이유만으로 대상 차량까지 같은 적용 구간이라고 판단하지 않음 |
| 대상 차량과 도로 | 차량·번호판·해당 표시·차량이 있는 도로의 연결을 확인 | 길 건너 또는 교차로의 다른 진입로 표지, 표지 뒷면, 학교 안 주차장, 다른 차량의 근거와 혼동 |
| 지도 자료와 일치 | 주변 여러 시설의 이름·주소·공식 지정 자료·사진 맥락을 대조 | 가장 가까운 학교 하나의 점, 이름만 같은 시설, 촬영자 좌표를 차량 좌표로 대입 |

색과 숫자는 추가 확인할 부분을 찾는 보조 단서로 쓴다. 빨간 포장이 없다고 보호구역을 배제하지 않는다. 표지와 노면 글씨가 둘 다 반드시 있어야 하는 규칙도 두지 않는다. 어느 하나와 도로 관계가 충분히 보이면 중복 사진을 요구하지 않는다.

사진의 시작·끝 표시와 카메라 방향을 이용해 관계를 살필 수 있지만, 카메라가 향한 방향은 차량 진행 방향이 아니다. 표지 적용 도로·차량 위치가 불분명하면 구간 안/밖을 확정하지 않는다. 다른 각도 상세사진도 같은 신고 건에 있다는 사실만으로 연결하지 않고 공통 지형·도로·대상 근거를 확인한다.

각 관찰은 사진 ID·원본 영역·대상 차량·읽은 문구·불명확 사유에 연결한다. 글자가 가려지면 추측으로 채우지 않고, 원본의 해당 부분과 전체 맥락을 다시 확인한다. 이 단계의 결과는 사진에서 확인한 근거이며 공식 지정·접수 판단과 구분한다.

### 지도에서 높일 수 있는 정확도와 한계

1. 위치·방향 품질을 확인하고 주변 여러 대상시설을 후보로 수집한다. 촬영자 위치·사진 위치·사용자가 지정한 차량 위치와 그 출처를 분리한다. 방향 품질이 나쁘면 배제 조건으로 사용하지 않는다.
2. 자료가 시설의 점 위치인지, 실제 지정 도로 구간/경계인지 표시한다. 점 자료만 있을 때는 근처 후보로 쓰고 원을 그려 확정 구역처럼 보여주지 않는다.
3. 공식 지정 구간·경계를 확보하고 위치를 충분히 연결할 수 있는 지원 지역에서는 사진 속 도로·차량 위치와 대조한다. 자료의 좌표계·대상 시점·관할·구간 의미를 확인하고 경계 부근의 위치 불확실성을 반영한다. 시작점과 끝점 두 개만으로 임의의 직선이나 면을 만들어 경계로 사용하지 않는다.
4. 공식 구간 자료를 확보하지 못한 지역은 사진 근거 확인을 계속하고 '구간 자료 미확인'으로 남긴다. 자료 없음·수집 범위 밖·조회 오류·확인된 지정 해제 상태를 구분한다. 표준 자료의 지정 여부가 비어 있으면 해제나 미지정으로 해석하지 않는다.
5. 자료의 제공기관·기준일·확인일·지정/변경 상태를 보존한다. 사진과 자료가 충돌하면 어느 근거가 충돌하는지 표시하고 자동 확정을 보류한다. 사용자의 지도 선택도 공식 구역 확인 결과로 바꾸지 않는다.

보호구역 지정 규칙은 주 출입문 기준 일정 반경 안의 도로 중 구간을 지정하는 방식이며 조건에 따라 범위가 확대될 수 있다. 따라서 현재 300m 후보 검색값을 법적 구역 경계로 쓸 수 없다. 후보 수집 반경·수량·비용 상한은 자료와 검증 결과에 맞춰 정하고, 범위 밖이라는 이유만으로 사진 근거를 부정하지 않는다. 카카오·네이버의 일반 지도 배경이나 검색 결과를 공식 지정 경계로 간주하지 않는다.

### 촬영 시간과 주민신고제 조건

- 보호구역 표시를 찾았다는 사실, 대상 차량과 구역의 관계, 주민신고제 대상 시설/도로·촬영 시간 조건을 별도 상태로 저장한다. 시간이 조건에 맞지 않더라도 사진에서 보호구역을 확인했다는 사실을 지우지 않는다.
- 관할 지자체의 확인된 공식 안내에 따라 대상 시설 종류·도로 구간·적용 요일/시간·사진 간격을 확인한다. 모든 학교·유치원·어린이집 보호구역이 같은 주민신고제 접수 범위라고 전제하지 않는다. 정문·교차로 구간 확인은 해당 지역 기준상 필요한 경우에만 요구한다.
- 앱의 현재 시간이 아닌 각 기본 사진의 촬영 시각으로 확인한다. 기존 출처별 촬영 시각 구분을 유지하며 시각을 알 수 없는 사진은 알 수 없음으로 남긴다. 사진의 밝기나 학교 문이 열린 모습으로 시간·휴일·방학을 추정하지 않는다.
- 공휴일 제외 규정이 적용되면 해당 연도의 검증된 공휴일 자료로 대체·임시공휴일도 확인한다. 달력 자료가 누락되거나 최신성을 확인할 수 없으면 '시간 조건 확인 필요'로 남기며 평일로 자동 통과시키지 않는다.
- 지역 규정·대상 구간·달력 정보가 부족한 것은 사진을 더 찍어도 해결되지 않는다. 이 경우 출처 확인·재조회·나중에 이어가기를 안내한다. 기존 전국 참고값을 보여줄 때도 해당 지역 요건이 확인됐다는 상태로 승격하지 않는다.
- 주민신고제 시간 조건에 맞지 않는다는 결과를 '주차해도 됨'이나 법적 단속 면제로 표현하지 않는다. 횡단보도·인도 등 동시에 보이는 다른 유형의 관찰도 보존한다. 최종 추천 순위와 확인 질문은 후속 5·6번에서 정리한다.

### 부족한 부분만 보완하는 사용자 흐름

| 현재 상태 | 원본·기존 자료에서 먼저 할 일 | 그래도 필요한 경우의 안내 |
| --- | --- | --- |
| 색칠된 바닥이나 숫자 30만 보임 | 주변 표지·노면 문구와 지도 후보를 재확인 | “차량과 어린이보호구역 표지 또는 바닥 글씨가 함께 보이도록 찍어 주세요.” |
| 보호구역 문구가 작거나 흐림 | 원본 부분 분석, 이미 있는 다른 사진 확인 | 문구 구분이 필요할 때만 표지/글씨 상세사진 안내 |
| 표지는 읽히지만 차량 도로와 연결되지 않음 | 기존 전체 사진의 도로·차량·표지 연결 확인 | “차량과 보호구역 표시, 두 곳이 있는 도로가 함께 보이도록 찍어 주세요.” |
| 끝 표시 근처라 구간 안/밖이 모호함 | 읽힌 표시 의미·대상 도로·공식 구간 자료 확인 | 사진으로 해결 가능한 경우에만 차량과 해당 표시의 관계가 보이는 보완 안내 |
| 번호판만 불명확함 | 원본 번호판 분석 | 해당 기본 사진 보완. 표지 상세사진으로 번호판 요건을 대신하지 않음 |
| 충분한 사진 근거가 있음 | 기존 근거 사용 | 불필요한 상세·전경 촬영 요구하지 않음 |
| 지도·지역 규정·공휴일 자료 또는 통신이 부족함 | 재조회·확인 필요 표시 | 무조건 재촬영을 요구하지 않음 |

추가 촬영은 안전한 보행 공간에서 가능한 범위로 안내하며, 학교 정문이나 구역 경계까지 이동하도록 일괄 요구하지 않는다. 할 수 없으면 미확인 사유와 기존 자료를 저장한다. 한 사진으로 여러 정보가 확인되면 중복 촬영을 요구하지 않는다.

기본 시간 비교 사진과 보완사진의 역할을 유지한다. 보완사진이나 잘라낸 영역으로 기본 두 장·촬영 간격·동일 차량 근거를 채웠다고 처리하지 않는다. 기존 사진·주소·수동 본문·선택은 교체 저장 성공까지 유지하며 취소·통신/저장 실패 후 이어갈 수 있어야 한다. 사진·차량·구역 후보·주소가 바뀌면 관련 결과를 재검토하고 늦은 이전 응답이 새 선택을 덮어쓰지 않도록 한다.

### 기술 변화와 검증 계획

1. 단일 `schoolZoneMarking`을 표시 종류·문구·시작/끝 의미·차량 도로와의 관계로 분리한다. 전체/원본 부분 분석 결과를 원본 ID에 연결하고 충분한 근거·불명확·해당 사진에서 미관찰·통신 실패를 구분한다.
2. 시설 점·공식 지정 구간·주민신고제 적용 구간을 다른 데이터로 표현한다. 기존 수집 파일과의 호환을 유지하면서 출처·범위·기준일·지정 상태를 확장하고, 지도 공급자의 배경 표시는 별도 보조 정보로 둔다. 전국 정밀 경계 확보를 완료한 것으로 전제하지 않는다.
3. 사진 관찰과 분리된 규칙 처리로 지역·구간·각 촬영 시각·공휴일을 확인한다. 조건 불충족과 근거 미확인을 구분하고, 필요한 확인 사항만 안내한다. AI가 운영 시간이나 지역 정책을 만들어 답하게 하지 않는다.
4. 웹과 iPhone에 같은 사진 역할·판독 상태·지역/시간 조건·미확인 안내·취소/보존 동작을 구현한다. iPhone의 AI·시설·지역 규칙 연결은 신규 작업으로 별도 기록한다.
5. 시험용 응답·위치·시간 자료로 색상만 보임, 노인보호구역 혼동, 학교와 가깝지만 다른 도로, 여러 시설, 구역 끝과 차량 관계, 점 자료만 있음, 지정 상태 공란/해제/상충, 자료 범위 밖, 평일 공휴일·시간 경계·촬영 시각 누락, 통신/저장 실패·취소·늦은 응답을 확인한다.
6. 사용할 권한이 있는 실제 사진을 확보하면 기존 방식과 비교해 표시 오인·놓침, 대상 도로 연결 오류, 불필요한 보완 촬영, 처리 시간·비용을 측정한다. 시간/지도 규칙 시험과 실제 사진 판독 정확도·실기기 촬영 결과를 구분해 보고한다. 현재 효과 수치나 보장하는 정확도는 없다.

## 10. 4-6 인도 — 확정 완료·구현 대기

2026-10-14 어린이보호구역 안 확정 후 제안한 다음 기본 유형이다. 사용자 화면의 유형명은 기존 '인도'를 유지하고, 근거 설명에서는 '인도(보도)'의 의미를 분명히 한다. 목표는 인도가 사진에 보이는 사실과 대상 차량이 그 공간을 차지한 것으로 보이는 사실을 분리하고, 진입로·건물 앞 공간·주차구획과 혼동되는 경우 필요한 근거만 보완하는 것이다.

**2026-10-14 사용자 확정: "인도도 이대로 확정. 다음 개선사항 진행해봐."** 아래 보도 식별·보이는 경계·대상 차량·바퀴/차체 관계·진입로/주차구획·통행 관련 관찰 분리, 원본 우선 보완·자료 보존·웹/iPhone 검증 계획을 확정하고 구현 대기로 전환한다. 다음 협의는 4번 공통 촬영·보완·이어하기 흐름이다. 전체 계획 확정 후 구현하는 순서를 유지하며 기능 구현·빌드·실기기 촬영·실제 인식 정확도 검증은 미착수다.

### 현재 코드와 개선 방향

- [판독 API](../api/vision.ts)는 `onSidewalk`에 '차가 보도(인도) 위에 올라가 있다'를 한 번에 묻고 `yes/no/unclear`를 받는다. 차량·보도 근거 상자는 있으나 보행 공간의 식별, 경계, 차량과의 관계, 진입로/주차구획 맥락이 별도 관찰로 나뉘지 않는다.
- [촬영 안내](../src/lib/crosscheck.ts)는 '보도 위에 올라선 바퀴'를 보여 달라고 한다. 보도 자체가 불분명한 경우와 바퀴/차체 위치가 불분명한 경우를 나눠 안내하도록 개선한다. 기존 유형 추천과 신뢰도 처리의 전체 우선순위는 후속 5번에서 정리한다.
- [거리 기준](../src/lib/rules.ts)에는 인도 거리값이 없으며 [주변 시설 추천](../src/lib/recommend.ts)에도 인도 경계 데이터가 연결되어 있지 않다. GPS로 인도 점유 여부를 이미 검증하는 기능이 있는 것으로 설명하지 않는다.

인도 식별에 경계석·점자블록·표지·분리 시설을 모두 필수로 요구하지 않는다. 해당 장소에서 보이는 근거의 조합과 연속된 보행 경로를 살핀다. 보행자전용 공간이나 자전거·보행 공간을 사진만으로 구분하기 어렵다면 '보도 여부 확인 필요'로 남기며 다른 법적 유형을 임의로 부여하지 않는다.

바퀴가 보도 쪽 지면에 놓인 것으로 보이는 경우와 차체 일부만 보도 쪽으로 나와 보이는 경우를 구분해 저장한다. '바퀴가 안 올라갔으니 해당 없음' 또는 '차체가 겹쳐 보이니 위반 확정'이라는 단순 규칙을 두지 않는다. 관찰한 부위와 불명확 사유를 보여주고 법적·지역별 처리 기준 확인과 연결한다.

차량 상자와 보도 상자의 겹침은 볼 영역을 찾는 단서로만 사용한다. 사진의 사각형 교차 면적을 실제 보도 점유 면적으로 바꾸지 않는다. 한 장의 사진으로 침범 깊이·남은 통로 폭을 cm 단위로 측정하거나 가려진 지면을 복원했다고 표시하지 않는다.

부분 사진만으로 보도인지 판단하지 않고 전체 맥락을 함께 사용한다. 원본 자르기나 별도 상세사진은 원본 ID·대상 차량·관찰 영역에 연결한다. 두 번째 기본 사진에서 이미 필요한 근거를 찾으면 중복 보완을 요구하지 않는다. 다만 한 기본 사진에 필요한 근거가 없는데 보완사진만으로 그 사진의 요건이 충족됐다고 처리하지 않는다.

촬영 위치 변경을 안내하더라도 안전한 보행 공간에서 가능한 범위로 제한하고, 차도로 내려가거나 차량 아래를 촬영하도록 요구하지 않는다. 보행 방해를 확인하기 위해 사람이나 유모차를 차량 옆으로 지나가게 하는 촬영을 요청하지 않는다. 가능한 사진으로도 관계를 확인할 수 없으면 미확인 사유와 기존 자료를 저장한다.

### 진입로·주차구획과 법적 판단의 구분

- 주차장 진입로에서 보도를 가로지르는 장면과 보도에 머물러 있는 장면은 구분이 필요하다. 사진 한 장, 차량 방향, 비상등, 운전자 탑승 여부만으로 출입 중인지 계속 정차 중인지 판단하지 않는다. 기본 시간 비교 사진의 시각·동일 차량·같은 자리 근거를 별도로 확인하며 두 시점 사이 계속 정차했다는 사실까지 자동 증명된 것으로 표시하지 않는다.
- 낮아진 턱이나 진입로가 있다는 사실만으로 보도가 끝났다고 보지 않는다. 실제 보행 경로와 경계를 살피되 사진으로 법적 도로 경계를 확정하지 못하면 그 상태를 남긴다.
- 도로교통법 제32조에는 보도·차도에 걸쳐 설치된 노상주차장 관련 제외 규정이 있다. 주차선이나 이용자의 말만으로 이 요건을 만족한다고 판단하지 않는다. 확인 가능한 공식 자료·현장 표지와 관련 지역 기준이 부족하면 예외 여부 미확인으로 남긴다.
- 춘천시 안내처럼 사유지 차량의 일부 보도 침범과 점자블록/통행 방해를 따로 다루는 지역 사례가 있다. 차체 일부 돌출·바퀴 점유·통행 관련 관찰을 나누되 해당 지역 기준을 전국 공통으로 적용하지 않는다. 사진으로 토지 소유 관계를 추측하지 않는다.
- 통행이 가능해 보이거나 보행자가 사진에 없다는 이유만으로 보도 점유 관찰을 삭제하지 않는다. 통행 방해가 모든 인도 유형에 반드시 필요한 추가 조건이라고 안내하지 않는다. 법적 요건·지역 접수 조건·시제품 관찰을 구분한다.

### GPS·방향과 자료 보존

현재 GPS·지도 연결은 주소·관할과 촬영 위치를 기록하는 데 활용한다. 일반 지도에서 차량 점이 보도 쪽으로 보인다는 이유로 실제 점유를 확정하지 않는다. 촬영 방향도 어떤 도로 쪽을 찍었는지 보조하는 정보이며 바퀴 접지 위치나 낮은 턱을 측정하는 기능이 아니다. 인도 경계 데이터가 없다는 사실은 사진 근거를 부정할 이유가 아니다.

기본 시간 비교 사진과 보완사진을 구분하고 보완 촬영 때문에 시간 계산을 초기화하지 않는다. 사진·주소·사용자 본문·수동 선택은 교체 저장 성공 전까지 유지한다. 취소·저장 실패 뒤 이어갈 수 있게 하며, 사진이나 대상 차량이 바뀌면 기존 관찰 연결을 재검토한다. 늦게 도착한 옛 분석이 새 선택을 덮어쓰지 않도록 요청 ID와 분석 대상 버전을 확인한다.

### 기술 변화와 검증 계획

1. 단일 `onSidewalk` 응답을 보도 식별·보이는 경계·대상 차량·바퀴/차체 관계·진입로/주차구획 맥락·통행 관련 관찰과 사유로 확장한다. 각 항목에 원본 ID와 영역을 연결하고 충분한 근거·불명확·해당 사진에서 미관찰·분석 실패를 구분한다.
2. 기존 모델을 이용한 전체/원본 부분 분석과 부족 사유별 안내부터 구현한다. 새 분할 모델, 정밀 깊이 추정, 실거리 측정을 확보한 것으로 전제하지 않는다. 최종 응답 형식과 호출 상한은 전체 계획 후 공통 구조에 맞춘다.
3. 차량과 보도가 모두 보였다는 사실만으로 위치 관계를 통과시키지 않는다. 사용자 수동 선택과 사진 관찰, 시간 비교, 지역 기준 확인을 분리한다. 추천 우선순위·확인 질문 전체 흐름은 후속 5·6번에서 정리한다.

### 지도 공급자와 위치 확인 흐름

권장 공급자는 **카카오 지도**다. 웹의 [주소 API](../api/address.ts)에 이미 Kakao 좌표→주소 경로가 있으므로 연결과 유지보수를 단순화하기 위한 선택이다. 카카오가 네이버보다 GPS 측정이 정확하다는 이유로 고르는 것이 아니다.

[GPS·지도 상세 계획](gps-map-location-plan-2026-10-14.md)의 지도 흐름도 함께 적용하도록 제안한다. 현재 내 위치·사진 촬영 위치·사용자 지정 차량 위치를 구별하고, 현재 위치 재취득과 사진 위치 복귀를 분리한다. 지도 이동만으로 기록을 바꾸지 않고 사용자가 위치를 적용했을 때 좌표·출처·선택 시각을 저장한다. 수동 주소는 명시적 변경 없이 덮어쓰지 않는다.

촬영 방향·정류소 후보 선정은 이미 확정한 계획을 유지한다. 정류소는 공공자료의 식별자·출처를 가진 별도 마커로 표시하며 지도 배경의 아이콘을 정류소 API 데이터로 가정하지 않는다. 위치 정보는 후보를 찾고 사진과 대조하는 보조 근거로 사용한다.

웹은 공식 JavaScript 지도 SDK, iPhone은 공식 iOS 지도 SDK와 네이티브 위치 수신을 연결한다. 지도 표시와 위치/판독 로직을 분리해 공급자를 바꿀 수 있게 하되 이번에 두 공급자 SDK를 동시에 개발하는 범위는 아니다. 기존 주소 경로·저장 자료·수동 입력 기능을 보존한다.

플랫폼 키·등록 도메인·앱 식별자 설정은 실제 SDK 연결 때 확인한다. 키가 없거나 지도 연결에 실패해도 사진 촬영·보관·수동 주소 입력은 계속할 수 있어야 한다. 모의 지도 검증과 실제 인증된 SDK 실행 결과를 구분해 기록한다. 현재 유효한 SDK 설정이나 비용 조건을 확보했다고 보고하지 않는다.

### GPS 품질의 초기 설정

다음 값은 위치 상태와 안내를 정할 초기값이다. 사진 속 차량의 실제 거리 판단이나 측정 정확도 보장값이 아니다. [상세 계획](gps-map-location-plan-2026-10-14.md)의 최신성·오차·일관성·권한 상태를 각각 평가하고 한 항목이 좋아졌다는 이유로 다른 문제를 지우지 않는다.

| 항목 | 권장 초기값 | 의미 |
| --- | --- | --- |
| 최근 위치 여부 | 위치 취득 후 5초 이내 | 그보다 오래되면 위치 갱신 필요. 촬영 자체는 계속 가능 |

| 새 위치 재확인 대기 | 최대 15초 | 기존 자료를 유지하고 재시도·지도 선택 제공. 사진 저장을 막지 않음 |

오래된 좌표·유효하지 않은 값·권한 제한·위치 변화가 크면 그 사유를 우선 표시한다. 샘플이 부족하면 일관성 미확인으로 남기고, 큰 오차 원이 겹친다는 이유로 좋은 품질로 승격하지 않는다. 사진을 찍은 뒤 들어온 좌표를 그 사진의 촬영 위치로 덮어쓰지 않는다.

이 값을 코드 곳곳에 흩어 넣지 않고 버전이 있는 공통 설정으로 관리한다. 웹과 iPhone의 입력 단위·권한·정확도 의미 차이는 각각 처리한다. 경계값 시험과 공개 자료/모의 입력 결과로 조정이 필요하면 변경 이유와 영향을 기록한다. 같은 기능 의미를 유지하는 값 조정은 구현 세부사항으로 다루며 매 숫자마다 재승인을 요구하지 않는다. 실제 거리 판정이나 촬영 차단 등 기능 의미를 바꾸는 경우에는 별도 협의한다.

### 이 범위안의 검증과 다음 순서

- 10개 유형 선택·저장·재열기·유형 변경 후 자료 보존을 확인한다. 전용구역/기타에 기본 6개의 조건이 잘못 적용되거나 자동 인식 완료로 표시되지 않는지도 확인한다.
- 교차로 사례는 기존 6절 시험을 적용한다. 지도 선택/취소/저장 실패/SDK 실패, GPS 5초·20m·50m 경계와 샘플 부족·중복 시각·큰 위치 변화·권한 제한을 검증한다.
- 카카오 계정과 플랫폼 설정이 준비되지 않았을 때도 나머지 코드를 진행할 수 있게 설계하고 실제 지도 연결 미검증 상태를 따로 보고한다. 비용·계정 설정이 필요한 조치는 구체적인 대상과 내용을 확인한 단계에서 다룬다.
- 전용구역 3개를 순서대로 협의·확정하고 기타·지도/GPS·교차로의 남은 결정을 정리한 뒤 원래 5번 '사진 근거 중심 유형 추천'으로 진행한다. 이어 6번 '확인 질문·사용자 선택 유지'를 협의한 뒤 전체 확정 범위를 구현한다.
